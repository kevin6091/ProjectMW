# Make Way — 클라이언트 개발 순서 및 설계 검토

**작성:** 2026-10-22 / v1.0  
**대상:** Unreal Engine **5.8.3**, Windows, 3인 Listen Server, 20개 작업일  
**예산:** A 120h + B 120h + C 클라이언트 72h + C TA 48h = **360인시**  
**범위:** 로컬 화면뿐 아니라 Listen Server에서 실행하는 게임 규칙·복제·패키지까지 포함한다.

## 1. 검토 결과와 현재 출발점

기존 방향인 **3인 멀티플레이 → 건설·주행 → 한 매치 → 콘텐츠 → 안정화**는 유지한다. 수정의 핵심은 차량의 상호작용 검증과 패키징을 앞당기고, D10 이전 경기 완성에 여유를 만드는 것이다. 4주 안에 모든 원안 콘텐츠를 확정적으로 제공할 수 있다는 근거는 아직 없다.

실제 확인한 현재 상태:

- `MW.uproject`의 Runtime 모듈은 `MW`, 엔진 연결은 `5.8`이다. 설치 엔진 `Engine/Build/Build.version`은 **5.8.3 / CL 58210709**이다.
- `Source/MW`에는 기본 모듈 파일과 Build.cs만 있으며, 현재 `Content`에서 게임 에셋 파일은 확인되지 않았다. 차량·트랙·경기 코드가 준비됐다는 전제로 일정을 잡지 않는다.
- 현재 경로에서 Git 저장소는 확인되지 않았다. D1에 실제 공유 저장소/Perforce 및 바이너리 관리 방식을 정한다.
- 이 검토는 문서·소스 파일·엔진 메타데이터·외부 자료를 근거로 한다. 게임 컴파일, 주행, 네트워크 품질, 패키징은 아직 검증하지 않았다.

검토 대상은 기획서, 클라이언트/TA 마일스톤, 두 마이그레이션 계획, 클라이언트/TA 개발명세서 **7개 전부**다. 큰 순서는 이 문서, 일별 일정은 `02_클라이언트_마일스톤_4주.md`, 시스템 계약은 클라이언트 개발명세서가 담당한다. 중복된 일별 표는 줄여 일정 불일치를 방지한다.

## 2. 큰 작업 순서 — 6단계

| 단계 | 작업일 | 만드는 것 | 다음 단계로 넘어갈 기준 |
|---|---|---|---|
| **1. 실행 기반과 차량 기술 검증** | D1~D3 | 접속·Framework·입력, 회색 상자 차량/도로, 원격 이동·충돌·외부 효과 시험 | 3인이 조작하고 충돌·임시 가속·넉백·텔레포트 후 제어를 회복한다. 이동 방식을 결정한다. |
| **2. 동시 트랙 건설과 주행 연결** | D2~D5 | 트랙 데이터·스냅·Ghost·서버 순차 확정·18초 제한·카메라 전환 | 3명이 동시에 선택·배치하고, 확정된 같은 코스를 달린다. 패키지에서도 접속·건설·주행한다. |
| **3. 아이템 없이 경기 한 판 완성** | D6~D8 목표 | 체크포인트·점수·복귀·결과·트랙 확장·경기 종료 | 3인이 2라운드 이상 진행해 결과와 재경기까지 간다. D9~D10을 통합 수정 여유로 둔다. |
| **4. 최소 아이템·위험·보조 통합** | D6~D10, 3단계와 병행 | 아이템 박스·부스터·가속 패드·범퍼, 슬롯 배치와 최소 HUD | **D10 필수 게이트:** 위 요소를 포함한 3인 매치가 패키지에서 끝난다. |
| **5. 검증된 구조 안에서 콘텐츠 확대** | D11~D14 | 트랙 총 5종 목표, 망치→기관총, 두 번째 위험 요소, UI·조작 개선 | 추가 기능마다 3인 회귀·패키지 확인. **D15 시작 시 기능 동결**한다. |
| **6. 릴리스 안정화와 증거 정리** | D15~D20 | 3PC 회귀·지연/손실·이탈·성능·릴리스 빌드·README | D18 릴리스 후보, D19~D20 최종 회귀·시연. 진행 불능/크래시 0, 재현 가능한 실행 자료. |

숫자 순서는 의존 관계다. A의 차량 검증과 B의 트랙 데이터 작업, 경기 규칙과 C의 최소 아이템 작업은 병행한다. **한 시스템을 완성한 다음 다른 시스템을 시작하는 방식으로 읽지 않는다.** D일차는 착수일 기준 상대 작업일이며 달력 날짜가 아니다.

### 1단계 — D1~D3: 가장 큰 위험부터 확인

- **A:** 차량 입력·카메라 최소판, 이동 후보 최대 2개 비교. 원격 플레이어의 조향과 차량 간 충돌, 경사 접지, 가속/넉백/복귀용 텔레포트를 시험한다.
- **B:** `AMWGameMode`/`AMWGameState`/`AMWPlayerState`/`AMWPlayerController`, 3인 접속과 Ready 최소판, 테스트맵·직선 트랙 스폰, 서버 상태 표시.
- **C:** 차체 1종과 규격이 같은 임시 도로부터 전달. 외부 원본·도구 조사는 D1의 TA 5h 안에서 종료하고, 확보되지 않으면 대체 에셋으로 전환한다.
- D2까지 첫 Windows Development 패키지, D3에 별도 프로세스 3개와 가능한 최소 LAN 2PC 접속을 확인한다. **D5에는 실제 3PC 패키지 건설·주행을 확인**한다.
- 조작감/보정 횟수/복귀 후 상태를 기록한다. 단순히 세 화면에 자동차가 보이는 것으로 이동 기술 검증을 끝내지 않는다.

### 2단계 — D2~D5: 프로젝트 고유 기능인 건설 완성

- B가 트랙 1종 수동 스냅 → 3종 데이터 기반 스폰 → 동시 요청·거절 → Ghost 갱신 → 시간 제한 순서로 구현한다.
- 직선·커브·완만한 경사를 우선하되, 경사 주행이 실패하면 D5까지는 평면 변형으로 시연한다. 경사는 조건부 콘텐츠로 남기고 실패를 완료로 표시하지 않는다.
- A는 로컬 건설/주행 카메라 및 입력 모드 전환을 담당한다. 차량 입력과 건설 입력의 중복 활성화를 방지한다.
- UI는 후보 선택·남은 시간·요청 대기·거절 사유만 먼저 만든다. 그래픽 완성보다 이 경로가 마우스로 끝까지 동작하는 것이 우선이다.
- 서버가 승인한 `PieceId + Transform + Sequence`가 결과다. 클라이언트가 보낸 월드 Transform은 배치의 진실로 사용하지 않는다.

### 3·4단계 — D6~D10: 경기 규칙과 상호작용을 나란히 통합

- **A:** 체크포인트 Trigger·실제 복귀, 외부 효과 API 확정, D8~D10에 로비/라운드/최종 결과 Widget 표시를 맡는다.
- **B:** 체크포인트 순서와 점수 → 라운드 종료 → 기존 트랙 유지·추가 → 매치 종료/동점/서든데스 → 이탈·시간초과 순서. 건설 위젯과 서버 데이터 계약도 유지한다.
- **C:** 박스·1칸 보유 → 부스터·가속 패드 → 범퍼 → 슬롯/피격/HUD 회귀 순서. 아이템 아트와 효과는 임시 리소스로 연결한다.
- D8의 아이템 없는 매치 목표와 D10의 최소 콘텐츠 포함 매치를 구분한다. D8 미완성은 D9~D10에 복구하며, D10 통과 전 3주차 추가 콘텐츠를 시작하지 않는다.
- 결과 판정은 **라운드 종료 때** 수행한다. 레이스 도중 목표 점수를 넘었다고 즉시 매치를 끝내지 않는다.

### 5·6단계 — D11~D20: 확대보다 회귀 비용을 먼저 계산

- 망치는 한 번의 근접 판정과 넉백, 기관총은 서버 제한 점사와 히트스캔으로 구성한다. 파괴·탄도·서버 과거 위치 되감기 판정은 이번 필수 범위에서 제외한다.
- 추가 트랙은 검증된 도로 변형을 우선한다. 경사/발사대가 점프·착지 안정성을 새로 요구하면 후순위로 둔다.
- 두 번째 위험 요소는 **정적 바리게이트**를 기본 후보로 삼는다. 범퍼와 달리 별도 가속 효과 없이 통행을 방해하며, 통행 폭 보존을 검증한다. 발사대는 D3 검증 결과와 잔여 시간에 따라 대체 채택할 수 있다.
- D15부터 새 기능을 넣지 않고, D18에 재현 가능한 3PC 릴리스 후보를 고정한다. D19~D20에도 QA 시간을 남긴다.
- 문서·영상·네트워크 로그는 각 게이트에서 수집한다. 마지막 이틀에 증거를 처음 만들지 않는다.

## 4. 차량 이동의 권장 선택 절차

**1차 후보는 엔진 제공 Chaos Vehicles 기반의 아케이드 튜닝**으로 시작한다. 차체·바퀴 구성이 어렵거나 네트워크 품질이 불충분할 때 비교할 후보를 하나만 둔다. 검증된 기존 구현이 없다면 커스텀 물리 예측 프레임워크부터 만들지 않는다.

| 후보 | 이 프로젝트에서의 판단 | D3 전에 확인할 것 |
|---|---|---|
| Chaos Vehicles | 차량 기능을 빠르게 시험할 첫 후보. 제공 기능으로도 아케이드 조작감/원격 충돌이 나오는지 확인해야 한다. | 현재 5.8.3의 실제 입력·복제 경로, 원격 충돌, 속도 제한·넉백·복귀 구현 가능성 |
| Chaos Modular Vehicle | 공식적으로 Network Physics/Resimulation을 지원한다. 다만 Geometry Collection/차량 모듈 구성 비용까지 포함해 비교한다. [S2] | 예제 기반 최소 차량을 정해진 시간 안에 만들 수 있는지, 차량 파괴를 비활성화한 상태의 안정성 |
| 커스텀 아케이드 Pawn + Network Physics | 조작감 자유도가 높지만 입력/상태 이력·스레드·재시뮬레이션까지 직접 책임진다. 관련 경험/재사용 코드가 있을 때 비교 후보로 적합하다. [S1, S3] | 원격 충돌·효과 재적용·텔레포트 이력 초기화까지 구현 가능한지 |
| Mover/ChaosMover | 최신이라는 이유만으로 기본 채택하지 않는다. 차량용 모드 작성·네트워크 백엔드 학습도 일정에 들어간다. [S4] | 필요한 차량 거동을 기존 모드로 구현 가능한지, 실험 기능 의존 범위 |

로컬 5.8.3의 `ChaosVehiclesPlugin.uplugin`, `ChaosModularVehicle.uplugin`, `Mover.uplugin`은 모두 `IsExperimentalVersion: true`다. 기본 Chaos Vehicles도 안정성을 보장받은 선택으로 취급하지 않는다.

`Replicate Movement`만 켠 커스텀 Pawn을 입력 예측/보정까지 완성한 솔루션으로 보지 않는다. 반대로 CharacterMovement를 차체 충돌·접지와 무관하게 강제하지도 않는다. D3 선택은 **고정 코스 3인 실험 결과와 남은 구현 비용**으로 판단한다. [S1]

선택 실패 시 D4에 학습할 기술을 무작정 추가하지 않는다. 검증된 대체 구현 도입과 LAN 중심 지원·단순 충돌 규칙으로의 범위 조정을 검토하고, 실제 주행이 통과하지 못하면 D5 게이트 실패로 기록한다. 일정표만 보고 성공 처리하지 않는다.

## 5. 구현을 단순하게 유지할 계약

1. **한 Runtime 모듈 `MW` + 필요 시 `MWEditor`.** `AGameModeBase`/`AGameStateBase` 조합과 프로젝트 Phase enum으로 시작한다. 엔진 MatchState와 별도 FSM을 이중 관리하지 않는다. [S5]
2. **Phase 표시와 준비 완료를 분리한다.** `Phase/RoundEpoch/PhaseEndServerTime`은 한 공용 구조체, 건설의 `Revision/Count/ExitTransform`은 TrackManager의 공용 구조체로 관리한다. 클라이언트는 트랙 Actor 및 충돌 준비 완료를 해당 리비전과 함께 응답한다. 서버는 Countdown 전 확인하고, 제한시간 내 준비하지 못하면 시작 취소/예외 종료한다. 클라 응답이 점수·배치를 결정하지는 않는다. [S6]
3. **한 번의 배치는 한 번의 확정이다.** 소유 Controller의 RPC, Phase/Epoch/후보/Revision/플레이어 완료 검사, 성공 Spawn/등록, 완료 플래그/리비전 갱신을 동기 처리한다. 실패 시 부분 등록을 남기지 않는다. 다른 Controller 사이의 전역 송신 순서는 보장하지 않고 서버 처리 순서를 사용한다.
4. **Pawn 수명을 먼저 단순화한다.** P0의 추락/파괴는 상태 전환+동일 Pawn 안전 이동으로 구현한다. 라운드 시작/종료와 복귀 때 아이템·임시 속도 효과를 비우고 물리 속도/입력 상태를 초기화한다. 실제 파괴 메시·Pawn 재생성은 후순위다.
5. **게임 판정은 서버에서 1회, 물리는 재시뮬레이션 가능.** 점수·픽업·슬롯 소모를 물리 재생 콜백에서 직접 실행하지 않는다. 예측 솔루션의 지원 경로로 가속/넉백을 적용하고 효과 ID로 중복을 막는다. 재생 중 외부 UObject를 임의 수정하거나 매번 FX를 발생시키지 않는다. [S1, S3]
6. **체크포인트 판정은 한 곳에서.** A는 TrackPiece에 부착할 Trigger와 서버 Overlap 후보 이벤트, B는 순서·중복·방향·점수의 최종 검사를 소유한다. 한 조각의 출구를 체크포인트로 사용하고, 마지막 인덱스가 결승 역할을 겸해 중복 점수를 막는다.
7. **작은 데이터 목록으로 시작한다.** 승인된 트랙/아이템 DataAsset을 참조하는 고정 카탈로그와 Replicated Actor를 사용한다. ID만 전송해도 패키지에 에셋이 포함되는 것은 아니므로 카탈로그 참조와 Cook 결과를 검증한다. 대규모 로딩 체계는 필요해질 때 확장한다. [S7]
8. **복제 상태→이벤트→Widget.** 서버 변경 경로와 원격 OnRep에서 동일한 로컬 갱신 함수를 호출해 호스트 HUD도 갱신한다. 위젯 생성 때 현재 상태를 한 번 읽고 이벤트를 구독한다. 타이머/속도처럼 연속 값 외의 UI에 매 프레임 폴링을 남발하지 않는다. [S9]
9. **GAS·Lyra 전체 구조·RepGraph·FastArray를 첫 작업으로 두지 않는다.** Lyra는 Game Feature/GAS/여러 모드까지 지원하는 학습용 대형 예제다. 책임 분리·입력·상태 흐름을 참고하되 이 프로젝트에 필요한 범위만 사용한다. 선택한 Network Physics 예제가 Iris를 요구하면 그 의존성은 함께 검증하고 고정한다. [S3, S8]
10. **TA는 내장 Data Validation부터 확장한다.** Runtime DataAsset과 Editor 검사를 구분한다. 일괄 임포터·전용 UI보다 잘못된 소켓/참조/체크포인트/슬롯을 실제 검출하는 것이 우선이다. [S10]

## 6. 범위와 일정 판정

| 구분 | 포함 범위 |
|---|---|
| D5 필수 | 차량 1, 계약을 만족하는 도로 3종, 동시 선택/서버 건설, 카메라 전환, 3PC 패키지 주행 |
| D10 필수 | 위 기능 + 2라운드 이상 확장/점수/안전 복귀/종료/재경기 + 부스터 1 + 범퍼 1 + 박스/가속 패드 + 최소 UI |
| D14 조건부 목표 | 트랙 총 5, 아이템 총 3, 위험 총 2, 보조 총 2, 차량 외형 1, 맵 1 |
| 이번 필수에서 제외 | 호스트 이전, 경기 중 참가/재접속 복구, Dedicated Server, 두 번째 맵, 차량별 물리, 루프/시소/기차, 체력·분해 파괴, 드리프트, 과거 위치 되감기 피격 판정 |

3인 전원 완주·항상 동일 순위·조각당 체크포인트 1개를 가정하면 선두의 라운드 점수는 `9, 18, 27…`, 3라운드 누적은 **54점**이다. 35점 목표는 이 가정에서 3라운드 종료를 만들 수 있다. 이는 **점수 산술 예시**이며 10~15분이라는 플레이 시간의 증거가 아니다. D8부터 건설/레이스/결과 시간을 따로 기록하고 D14에 목표 점수를 조정한다.

4주/360인시는 작은 팀의 **조건부 목표**로 유지한다. C에게 늦은 추가 HUD 작업을 모두 넘기거나, B가 2개 대형 시스템과 모든 UI를 동시에 완성한다는 가정은 제거한다. D3·D5·D10 실패 시 남은 작업을 재산정하고 조건부 콘텐츠를 먼저 줄인다. 원안 수량 대비 실제 포함/보류를 릴리스 노트에 적는다.

정상 건설 라운드는 참가 인원 N조각을 추가한다. 공간 부족 등으로 유효한 대체 조각도 설치할 수 없으면 `ConstructionBlocked`로 예외 종료하고 원인을 표시한다. 이 경우 N개 추가 완료/정상 매치 완료로 기록하지 않는다.

최소 QA는 매 게이트에서 정상·중복·오래된 요청·지연/손실·시간초과·원격 이탈을 확인한다. D3부터 무지연 기준과 **관측 RTT 약 100ms** 조건을 비교하고, D8부터 손실 조건도 추가한다. 에뮬레이터 송수신 지연 설정과 실제 관측 RTT를 따로 기록한다. 악조건 진행성 검사와 쾌적한 주행 품질의 합격은 구분한다. [S11]
