# Make Way — 클라이언트 마이그레이션 실행계획

> v1.0 · 작성 목적: **기존 코드/프로토타입/게임플레이 데이터가 있을 경우 UE5 C++ 프로젝트로 이식하는 절차**를 정의한다.  
> 관련 일정: `02_클라이언트_마일스톤_4주.md` · 담당 A/B/C  
> **중요:** 현재 제공된 개발기획서에는 '이미 구현한 원본 클라이언트 프로젝트·기존 브랜치·소스 코드 목록'이 명시되지 않는다. 따라서 실제 이식 대상은 **미확정**이다.

> **2026-10-22 실행 기준 보완:** 로컬 대상은 **UE5.8.3 / MW Runtime 모듈**이며 기본 모듈 외 게임플레이 소스는 확인되지 않았다. 외부 원본의 존재는 별도 확인 대상이다. 원본이 없으면 D1 조사로 이식 검토를 종료한다. 일별 일정·API 시점은 마일스톤 v1.1이 우선한다. 효과 API는 D3 시험/D5 계약, 첫 패키지는 D2, D5 실제 3PC 건설·주행, D10 실제 3PC 매치, D15 동결이다. 이 문서의 후반 QA/이관 단계가 최초 패키지 시험을 뒤로 미루지 않는다.

## 1. 용어와 이번 프로젝트의 정확한 범위

| 활동 | 명칭 | 사례 | 이 문서 처리 |
|---|---|---|---|
| 본인이 소유한 UE4/UE5/Unity/기존 프로젝트 코드를 현재 UE5로 옮김 | **Migration / Porting** | 기존 Vehicle BP/코드를 새 C++ 구조로 이식 | 이식 대상으로 등록된 경우에만 실행 |
| 기존 Prototype의 기능을 새 아키텍처로 교체 | **Refactoring / Reimplementation**, 상황에 따라 Migration | 프로토타입 Movement를 공용 Vehicle Component로 교체 | 원본 구현의 기능·데이터가 실제 존재하면 이관 기록 |
| Make Way 플레이를 관찰하고 UE5에서 시스템을 처음 만듦 | **Reverse engineering of behavior / Reimplementation** | 트랙 건설/체크포인트 규칙을 C++로 새로 구현 | **마이그레이션으로 부르지 않음** |
| 기능 브랜치를 `main`에 합침 | **Integration / Merge** | `feature/vehicle` PR 통합 | 마이그레이션이 아니라 공통 개발 프로세스 |
| UE 프로젝트에서 콘텐츠 에셋을 옮김 | **Asset Migrate** | StaticMesh/Materal 복사 | TA 마이그레이션으로 관리 |

### 소스가 아예 없을 경우의 결론

- **이전할 클라이언트 원본이 없다면 '클라이언트 마이그레이션 완료'라는 성과를 만들지 않는다.** 이 계획의 M0 판정 결과를 `No source → migration not applicable`로 기록한다.
- 그 경우 A/B/C는 즉시 `02_클라이언트_마일스톤_4주.md`의 **신규 C++ 구현**으로 넘어간다.
- D5 이후 기존 프로토타입을 정식 인터페이스로 바꾸는 작업이 생긴다면, 그때는 출발/도착 코드·변경 책임·동작 동등성 테스트를 기록하고 **실제 이관 작업으로 등록**한다.

## 2. 출처 조사/이관 대상 결정 게이트 (D1~D2)

| 확인 항목 | 수집할 증거 | 판정 |
|---|---|---|
| 원본 리포지토리/브랜치/커밋 | 정확한 URL·commit hash·작성자 | 없으면 이관 후보 제외 |
| 원본 프로젝트와 엔진 버전 | `.uproject`, `.uplugin`, Build.cs 또는 다른 엔진 버전 | 포팅 난이도 산정 |
| 코드/Blueprint의 실행 여부 | 빌드·플레이 영상/로그 | 실행 안 되면 재작성 비용 비교 |
| 복제/네트워크 권한 설계 | 서버/클라 역할, RPC/Owner, 복제 프로퍼티 | Unreal 서버 권한 모델에 재검증 |
| 3인 협업 사용 권한 | 코드·에셋 라이선스/기여 소유 확인 | 권리 미확인 시 복사 금지 |
| 유지보수 비용 | 구조적 의존성, Blueprint 참조, 구현 겹침 | 새 구현보다 비싸면 이식하지 않음 |

### 결정 규칙

1. **직접 이식(Port):** 프로젝트 버전·라이선스 명확, 컴파일/빌드 가능한 코드, 현재 구조와 호환, 도입 검증이 구현보다 짧다.
2. **데이터만 이전:** 기존 DataTable/DataAsset/설정값은 유효하지만 Gameplay 코드는 리팩터링 부담이 큰 경우.
3. **행동만 참조해 신규 구현:** 원본은 관찰 가능한 게임플레이뿐이거나 독점 바이너리/재사용 권한이 없는 경우.
4. **보류/폐기:** 출처·권한/엔진 호환 미확인 또는 마이그레이션으로 핵심 마일스톤 위험이 커지는 경우.

## 3. 이관 레지스터 (실제 소스 확인 전엔 전부 가정)

| 후보 시스템 | 담당 | 원본 존재? | 이관이 적합한 경우 | UE5 목표 | 필수 회귀 검사 |
|---|---|---|---|---|---|
| 차량 이동/카메라 | A | **미확정** | 검증된 예전 Vehicle Pawn/Movement가 있을 때 | 차량 C++/BP 구성 | 입력·충돌·원격 보정·서버 소유권 |
| 트랙 배치/연결 데이터 | B | **미확정** | 기존 소켓/조각 목록/배치 프로토타입이 있을 때 | 서버 TrackManager/DataAsset | 동시 배치/간섭·중복 요청 |
| 상태/점수/라운드 | B | **미확정** | 기존 Match Prototype이 있을 때 | GameMode/GameState/PlayerState | 상태 복제/한 판 종료/이탈 |
| 아이템/위험 판정 | C | **미확정** | 자체 이전 버전의 Item/Hazard 코드가 있을 때 | 서버 권한 Item/Hazard Component | 피격 권한·인벤토리·HUD 일치 |
| UI/입력 매핑 | 각 소유자 | **미확정** | UMG·Input Mapping Asset이 재사용 가능할 때 | 소유자별 UI·Input | 로컬 화면·Pawn 교체/재접속 |
| 원작 Make Way 로직 | 전원 | 재사용 허가 **없음/확인 안 됨** | 원작의 독점 코드가 없거나 권한이 불명확하면 이식 불가 | **플레이 관찰에 기반한 신규 구현** | 비교 영상/체험, 저작권 출처 명시 |

원본이 확인되면 각 행마다 아래 필드를 추가한다.

```text
MigrationTicket:
  SourceRepo / SourceCommit / OriginalOwner
  OriginalEngineVersion / TargetEngineVersion
  SourceFiles / TargetFiles / Dependencies
  ExistingBehavior + Video/Log
  Port/Rewrite/Discard 결정 및 근거
  NetworkAuthority/Ownership 변경점
  AcceptanceTest + RollbackCommit
  ResponsibleReviewer
```

## 4. 단계별 이식 프로세스

### C-MIG-0 인벤토리와 판정 (D1)

- A/B/C 각자 기존 코드나 BP가 있는지 보고, 커밋과 실행 증거 확인.
- 기획안만 있고 원본 코드가 없으면 이관 대상 0개로 등록하고 종료. 이 단계는 **마일스톤 CL-M0와 겹치는 조사 업무**로 처리하며 시간을 추가하지 않는다.
- 이식 후보가 있을 때만 담당자별 각 업무의 D2~D5 세부 작업 시간을 재배치한다.

### C-MIG-1 인터페이스 고정 (D2)

- B: `TrackPieceDefinition` 스키마, 서버 배치 요청/응답과 매치 Phase 계약.
- A: 차량 입력·이동/넉백 API, Checkpoint·Respawn 이벤트 계약.
- C: 인벤토리·아이템 상태, HazardSlot 연결, HUD 표시 데이터 계약.
- 코드 포팅은 인터페이스에 맞춰 적응. **기존 코드의 무분별한 Copy-Paste나 BP 일괄 변환을 하지 않는다.**

### C-MIG-2 최소 단위 Port + A/B 테스트 (D3~D5)

- 이관 후보 기능별 최소 1개 동작을 현재 프로젝트에서 **독립 테스트** (예: 차량 1대, 트랙 1조각, 아이템 부스터 1개).
- 소유권·월드 컨텍스트·UObject/GC 수명·Replication을 다시 확인한다. 다른 엔진/프로젝트의 RPC 이름만 바꿔서는 동작 동등성을 보장하지 않는다.
- 원본 구조가 신규 설계보다 부적합하면 포팅을 중단하고 기존 동작 영상을 근거로 재구현.
- D5 통합 데모에 꼭 필요한 후보만 적용. 핵심 기능을 막는 이식 작업은 **포기**할 수 있다.

### C-MIG-3 매치 루프 통합 (D6~D10)

- Server Authoritative Checkpoint/점수/아이템 판정으로 이관된 시스템을 통합.
- 레이스가 매치 1회 종료까지 진행되지 않으면 나머지 이식 기능은 동결. 기본 레이스의 복귀 조건(선두 다음 유효 체크포인트), 건너뛴 체크포인트 미지급 규칙도 회귀 검사.
- 포팅 시 원본 BP/데이터·참조가 남아도 기능이 중복 실행되지 않게 단일 활성 코드 경로 보장.
- D10 Gate: 실제 이관된 기능의 원본 대비 동작 체크 + 3인 기본 매치 종료.

### C-MIG-4 경로 정리/부채 제거 (D11~D15)

- 더 이상 쓰지 않는 프로토타입/Blueprint 경로 폐기 여부 결정.
- DataAsset/Blueprint 리다이렉터, 참조 깨짐, 공용 소스 통합 충돌을 확인.
- 이관 시점 이후 신규 변경이 계속 가능한 곳(설정값)과 동결할 공용 인터페이스를 구분.
- D15 이후 이식/교체 신규 요청 금지. **Critical 버그를 해결하는 최소 변경**만 허용.

### C-MIG-5 QA·롤백·기술 문서 (D16~D20)

- 각 Ticket마다 이식 전/후 증거, 회귀 QA, 실패와 해결 기록.
- 패키징 성공·별도 PC 3인 테스트. Listen Server 동작만을 근거로 Dedicated Server 지원을 주장하지 않는다.
- 원본 라이선스가 불분명한 코드와 에셋은 최종 공개 배포에서 제거.

## 5. 포팅의 난이도/경제성 판정

| 판정 요소 | 낮은 위험 | 높은 위험·권장 행동 |
|---|---|---|
| 원본 수준 | UE5 내 검증된 단일 Component | 엔진이 다른 핵심 물리 제어 / 행동 참조 후 재구현 |
| 의존성 | 단순 DataAsset, 적은 참조 | 많은 BP 그래프와 복제 복잡도 / 이식 중단 |
| 멀티플레이 | 소유권·서버 판정이 이미 명확 | 로컬 단일 플레이 코드 / 네트워크 재설계 비용 산정 |
| 일정 | D5 게이트를 지연시키지 않음 | D5/D10을 늦춤 / 원본 대신 신규 최소 버전 |
| 법적 허가 | 작성자/라이선스 명시 | 상용 게임 독점 소스·에셋 / 배포·복사 불가 |

### 예시 의사결정

- 재사용 가능한 `InputMappingContext` 하나가 있다 → 유지/복사하되 엔진 버전·Pawn 소유권 체크.
- 자체 제작된 C++ Vehicle Movement가 있지만 멀티플레이 검증 안 됨 → D3 3인 테스트 후 선택. 검증 실패 시 새 구현.
- 원작 Make Way의 플레이 방식만 관찰함 → **마이그레이션이 아니라 벤치마킹 기반 재구현**. 같은 이름으로 포트폴리오에 기술하지 않음.

## 6. 3인 팀에서 코드를 이식할 때 필요한 통합 테스트

| Gate | A — 차량 | B — 서버/트랙 | C — 아이템/위험 |
|---|---|---|---|
| 단위 | 입력/가속/충돌·포지션 | 소켓·배치 후보/서버 거절 | 획득·보유 1개·사용/소진 |
| 네트워크 | 서버-클라 이동 상태 차이 기록 | 동시 배치 순서·Duplicate RPC | 소유권 없는 아이템 사용/중복 획득 거부 |
| 라운드 | 죽음/복귀 후 Vehicle 참조 안정 | 라운드 전환 후 점수/트랙 유지 | 라운드 종료 시 아이템 상태 reset 정책 |
| 패키지 | 별도 3PC 접속·차량 조작 | 매치 시작~결과 종료 | HUD/피격/이펙트 정상 |

### 롤백 원칙

1. 마이그레이션 Ticket당 PR 1개와 되돌릴 커밋/태그 지정.
2. 기존 정상 빌드와 이식 분기의 테스트 결과를 비교.
3. Crash/중복 서버 액션/패키지 실패가 발생하면 해당 이관을 격리하고 마지막 정상 통합 상태로 복구.
4. 도입 전후에 동작 차이가 있다면 **설계 변경인지 버그인지** 분류하고 팀의 승인을 받는다.

## 7. 일정에 반영하는 실제 방식

- **이관할 소스 없음:** D1 조사 후 이 문서의 후속 이식 작업은 적용하지 않는다. A/B/C의 120/120/72시간은 신규 개발에 전부 사용.
- **소규모 기존 코드 있음:** D2~D5의 관련 기능 개발 시간 안에 이식·동작 확인을 포함. 순수 시간 절감은 검증 전 주장하지 않는다.
- **대규모 기존 코드 있음:** 4주짜리 전면 포팅 프로젝트로 바꾸지 않는다. CL-M1/M2에 도움이 되는 최소 모듈만 선정; 나머지 재구현 또는 보류.
- **TA 원본 AssetFlow/외부 에셋 사용:** 클라이언트 포팅으로 중복 집계하지 않고 `03_TA_마이그레이션_실행계획.md`에서 추적.
