# 현재 방 목록 → 참가 → 로비 동기화 구현 및 검증

검증일: 2026-10-28. 분야: Client + Server. 엔진: UE 5.8.4.

> 2026-10-29 화면 후속 적용: 아래 MW 기능·API·에셋 경로를 유지한 채 Frontend Designer를 이식하고 실제 2인 참가·이탈·재참가·종료를 재검증했다. 현재 화면과 기능 분리 기준은 [13번 통합 문서](13_Frontend_디자인과_MW_방참가_기능_통합.md)를 참고한다.

## 1. 현재 완료한 흐름

```text
L_Title에서 실제 EOS 로그인
 → 경기 참가 → 현재 공개된 MW 방 목록 자동 조회
 → 방 선택 → 참가 확인 → EOS JoinSession
 → 호스트 주소 확인 → ClientTravel → 기존 Listen Server 로비 합류
 → 서버 방 설정·본인 PlayerState·EOS 참가자 등록 확인 → Joined
 → 두 창에서 같은 참가 인원·이름·방 안의 ID 표시
```

조건을 입력하는 검색창은 만들지 않았다. 화면에는 방 목록, 새로고침, 선택한 방, 참가 확인, 뒤로 가기, 진행·오류 안내가 있다. 내부에서는 EOS Sessions의 `FindSessions` API로 공개된 방을 조회한다. 별도 방 목록 서버나 유료 서비스를 추가하지 않았다.

목록은 **조회 시점의 스냅샷**이다. 진입 시 자동 조회하고 이후 새로고침으로 갱신한다. 서비스가 돌려준 같은 버킷·프로토콜의 Lobby 상태 방을 최대 100개 처리한다. 전 세계의 모든 방을 실시간으로 보여 주는 전역 목록이라는 뜻은 아니다. 최종 입장은 EOS와 서버가 다시 판정한다.

Ready 변경·경기 시작·차량 스폰은 후속 작업이다. 기존 로비의 Ready와 경기 시작 버튼은 계속 비활성 상태다.

## 3. 목록과 참가 API

```cpp
void RequestRefreshRooms();
TArray<FMWRoomInfo> GetAvailableRooms() const;
int32 GetRoomListRevision() const;
void RequestJoinRoom(const FString& SessionId, int32 ListRevision);
```

FMWRoomInfo에는 SessionId, RoomName, CurrentPlayers, MaxPlayers, MapThemeId, bCanJoin, UnavailableReason을 담는다. 원본 FOnlineSessionSearchResult는 Subsystem이 보관한다. Widget은 서버 주소나 레벨 경로를 만들지 않는다.

선택할 때 **세션 ID + 목록 리비전**을 저장한다. 같은 이름의 방이나 정렬 순서가 바뀐 목록을 혼동하지 않도록 방 이름·배열 인덱스로 참가하지 않는다. 새로고침하면 선택을 초기화하고 이전 리비전의 참가 요청은 거절한다.

완료 알림은 OnRoomsUpdated와 OnJoinRoomFinished이며, 진행·실패는 기존 OnSessionStateChanged와 OnSessionError로 갱신한다. Construct에서 현재 상태를 읽고 구독하며 Destruct에서 자기 구독을 해제한다. Tick 폴링은 추가하지 않았다.

| 상태 | 화면 동작 |
|---|---|
| 로그인 완료 + None | 목록 조회·선택·뒤로 가기 가능. 현재 선택이 유효하고 bCanJoin일 때 참가 가능 |
| Searching | 조회 중 안내. 새로고침·선택·참가·뒤로 가기 잠금 |
| Joining | 연결·로비 확인 중 안내. 중복 참가와 뒤로 가기 잠금 |
| Joined | 기존 로비 표시. 나가기 가능 |
| Leaving | 정리 중 안내·조작 잠금 |
| CleanupRequired | 새 생성·조회·참가 금지. 정리 재시도/재시작 안내 |

서비스 요청 제한시간은 현재 60초다. 요청 진행 중 시간만 초과하면 완료 Delegate를 임의 삭제하거나 새 요청을 겹치지 않는다. 늦은 완료를 받아 기존 정리를 이어 간다.

## 4. 서버와 복제의 완료 조건

EOS JoinSession 성공은 온라인 세션 참가 성공이다. 게임 서버 접속과 로비 동기화까지 끝났다는 뜻은 아니다. 현재 구현은 다음 조건을 확인한 뒤 Joining → Joined로 바꾼다.

1. 자기 GameInstance의 로컬 Controller가 실제 Client 월드에 존재한다.
2. 맵 이동 완료 후 NetDriver, MWGameState, 본인 MWPlayerState가 준비됐다.
3. 서버 GameState의 실제 세션 ID·테마·현재 맵이 선택한 방과 일치한다.
4. 본인 PlayerState의 인증 ID가 현재 로그인한 사용자와 일치한다.
5. 본인이 GameState.PlayerArray에 있고 서버 발급 ID와 EOS 참가자 등록 완료 상태를 받았다.

현재 GameState 계약은 다음과 같다. **10번 가이드의 최초 호스팅 예제에 있던 인자 한 개 버전과 다르다.** 생산자인 GameMode와 소비자인 Subsystem을 함께 적용해야 한다.

```cpp
void ApplyRoomSettingsFromServer(const FMWRoomSettings& Settings, const FString& SessionId);
FString GetRoomSessionId() const;
```

GameMode는 Sessions->GetActiveRoomSessionId()로 실제 세션 ID를 가져와 승인 방 설정과 함께 적용한다. RoomSettings와 RoomSessionId 모두 RepNotify로 복제한다.

PlayerState의 LobbyMemberId는 서버가 PostLogin에서 1부터 순서대로 발급하는 **현재 방 안의 참가자 번호**다. 화면의 ID 01, ID 02는 EOS의 개인 식별자나 영구 계정 번호가 아니다. 계정 이름은 엔진 PlayerName으로 표시한다. 나간 뒤 재참가하면 새 번호를 받으며 기존 번호를 당겨 재사용하지 않는다.

GameMode는 실제 EOS RegisterPlayers 완료를 관찰하여 bSessionRegistrationConfirmed를 서버에서 갱신한다. 원격 등록 실패 시 참가자를 내보낸다. 유효하지 않은 인증 ID와 같은 계정의 중복 입장도 서버에서 거절한다. 복제 도착 순서를 가정하지 않고 GameState/PlayerState/Controller의 변경 이벤트마다 준비 조건과 로비를 다시 확인한다.

맵 테마 정본은 그대로 **MWAssetData → MWAssetManager**다. 목록의 전체 테마 ID를 로컬 카탈로그로 검사하며 지원하지 않는 방에는 참가 불가 사유를 표시한다. 참가 후 방 이름·정원·테마·인원은 서비스 목록의 옛 값이 아닌 서버 GameState/PlayerState를 읽는다.

## 5. 검증 중 수정한 문제

### UE 5.8 EOS 목록의 빈 슬롯 필드

설치된 OnlineSessionEOS.cpp의 AddSearchResult가 EOS의 NumOpenPublicConnections를 검색 결과의 NumOpenPrivateConnections에 기록하는 것을 확인했다. 공용 슬롯만 읽으면 호스트 1명인 방도 3 / 3명으로 잘못 표시됐다.

프로젝트는 private 슬롯을 0개로 제한하므로 공용·비공용 필드의 **남은 슬롯 합계**로 현재 인원을 계산한다. private 정원이 있는 외부 결과는 표시 대상에서 제외한다. 수정 후 같은 실제 방이 1 / 3명, 참가 가능으로 표시됐고 실제 참가도 성공했다. 엔진 소스는 수정하지 않았다.

### 맵 이동 전 연결 실패

엔진은 PendingConnectionFailure를 World=nullptr, PendingNetDriver로 전달할 수 있다. GameNetDriver와 유효한 World만 받는 기존 방 생성 가드는 이 실패를 놓칠 수 있었다. 참가 중에는 해당 PendingNetDriver의 WorldContext에서 **소유 GameInstance까지 일치하는지** 확인하고 실패·정리를 처리하도록 보완했다. 다른 PIE의 실패를 자기 참가 실패로 처리하지 않는다. 이 분기는 코드와 최종 정상 빌드로 확인했으며 미응답 주소로 접속하는 강제 실패 시험은 하지 않았다.

위젯 조작은 Unreal MCP로 실제 인스턴스의 OnClicked를 호출했고, 표시 결과는 실제 TextBlock과 서버/클라이언트 Actor 상태를 교차 확인했다. 화면 제어가 Esc로 중지된 상태여서 최종 목록·로비의 픽셀/마우스 좌표 검사는 수행하지 않았다.

최종 재시작 점검 뒤 PIE 중지 요청 직후 긴 Python 기록 스크립트를 보낸 과정에서 에디터가 한 번 종료됐다. 스크립트의 기록 저장은 끝났고, 충돌 스택은 RiderLink/RiderAgentTools의 RPC 결과 반환(Property/RdEndpoint/PythonExecutor)에 있으며 MW 게임 함수는 나타나지 않았다. 자동화 도구의 요청 수명 문제로 추정하며 게임 접속 시험 통과와 구분한다. 로그는 Saved/RoomJoinIntegration/RiderLink_RPC_Crash.log에 보존했다. 에디터를 다시 연 뒤 PIE 실행 → Play 확인 → 중지 → Idle 확인을 순차 수행하여 정상 종료와 에디터 생존을 확인했다. 도구를 수정하거나 비활성화하지 않았다.

3PC·서로 다른 인터넷 회선·3~4인 정원 초과 경쟁·동시에 여러 호스트 방·Cook/패키징은 아직 시험하지 않았다. 이번 성공은 실제 EOS를 이용한 한 PC 두 계정의 접속·동기화 검증이다. 정리 서비스 무응답과 연결 시간초과의 강제 주입도 최종 런타임 시험에 포함하지 않았다.

세부 JSON과 빌드 로그는 Saved/RoomJoinIntegration/에 있다. 변경 전 사본은 그 아래 Before/에 보관했다. Content는 Plastic SCM 관리 대상이며 새 위젯도 추가 상태로 보존했다. Git 커밋·푸시와 Plastic 체크인은 하지 않았다.

## 7. 사용자가 다시 시험하는 순서

1. L_Title에서 **New Editor Window PIE / Players=2 / Net Mode=Play Standalone / Run Under One Process=켬 / Dedicated Server=끔**으로 실행한다. 처음부터 Listen 모드로 띄우지 않는다. 방 생성 기능이 Listen Server를 시작한다.
2. 첫 창과 두 번째 창에서 서로 다른 EOS 계정으로 로그인한다. 같은 브라우저 계정이 자동 선택되면 인증 화면에서 계정을 전환한다.
3. 첫 창에서 경기 생성 → 이름 입력 → 정원 3명 → 테마 Asset.MapTheme.DevDefault → 생성 확인. 로비에서 1 / 3명을 확인한다.
4. 두 번째 창에서 경기 참가를 누른다. 이미 목록 화면이면 새로고침한다. 첫 창의 방과 1 / 3명, 참가 가능 표시를 확인한다.
5. 방 한 줄을 선택한 뒤 **참가 확인**을 누른다. 연결 중에는 버튼이 잠겨야 한다.
6. 양쪽에서 같은 방 이름·테마·정원, 2 / 3명, 서로 다른 두 이름과 ID, 호스트 구분을 확인한다.
7. 참가자가 나가기를 누르면 호스트는 1 / 3명, 참가자는 로그인된 타이틀로 돌아와야 한다.
8. 다시 참가한 뒤 호스트가 방 종료를 누른다. 두 창 모두 타이틀로 돌아오는지, 새로고침에서 방이 사라졌는지 확인하고 PIE를 Stop한다.
