# MW 공용 데이터 기반 이식

적용 분야: Client + Server 공용 Runtime 데이터. 기준 엔진: UE 5.8.3.
원본: [Khazan 0f04ac9](https://github.com/kevin6091/Khazan/commit/0f04ac939de21e57b80e9c774eb64308e0297aed).
이 문서는 원본을 그대로 복사한 기능 목록이 아니라 이번 MW 구현의 계약과 연결 순서다.

## 1. 단계와 범위

| 단계 | 산출물 | 확인할 조건 |
|---|---|---|
| 1. 에셋 기반 | `UMWAssetData`, `UMWAssetManager`, 엔진 설정 | ID/라벨 조회, 명시적 로딩, 중복 ID 거부, GC 보관/해제 |
| 2. 입력 기반 | `UMWInputData`, 네이티브 입력 태그 | 모드별 MappingContext, 정확한 액션 조회, 잘못된 입력 정의 진단 |
| 3. 플레이 대상 정의 | `UMWVehicleDefinitionData` | 안정 VehicleId, 서버가 선택할 PawnClass, 주행 InputData |
| 4. 실제 콘텐츠 연결 | 승인된 DataAsset, 차량 Pawn/Controller | 로컬 매핑 등록/해제, 서버 스폰, 3인 검증, Cook/패키지 |

1~3단계는 이번 소스 구현 범위다. 4단계의 차량/Controller/게임 규칙은 아직 존재하지 않으므로 구현된 것으로 간주하지 않는다.
현재 맵과 Blueprint를 수정하거나 테스트용 APawn을 실제 차량으로 등록하지 않는다.
기능 일정의 원본은 기존 마일스톤이며 이식만으로 해당 게이트를 통과한 것은 아니다.

**2026-10-22 후속 설계 채택:** 현재 실제 타입명은 `UMWVehicleDefinitionData`다. 차량 입력·Movement·공용 주행 설정·효과 구조와 시각 자료는 [07 상세 설계](07_차량_입력_이동_효과_설계.md)를 따른다. 후속 제작한 입력 IA/IMC의 확인 결과는 아래 6.2절에 기록한다. Brake/Drift 태그와 입력을 소비하는 런타임 타입은 아직 추가되지 않았다. 건설 선택/배치 분리와 회전 의미는 [개발명세 4.5절](MakeWay_클라이언트_개발명세서_v1.0.md)이 원본이다.

## 2. 원본에서 유지/제거한 책임

| 원본 | MW 타입 | 유지한 설계 | 제외/수정 |
|---|---|---|---|
| KZAssetData | MWAssetData | ID, soft object 참조, 라벨 | 파일명 접두사로 `_C`를 붙이지 않음. 작은 목록을 직접 조회해 편집 후 파생 맵이 낡는 문제를 제거 |
| KZAssetManager | MWAssetManager | 명시적 로딩, 강한 참조 캐시, 해제 | 엔진 StartInitialLoading으로 초기화. 임시 싱글턴 생성, basename 캐시, 조회 중 숨은 로딩 제거 |
| KZInputData | MWInputData | InputTag → InputAction, MappingContext | GAS/전투 명령 없음. 중복/누락 입력 정의 검사 |
| KZCharacterDefinitionData | MWVehicleDefinitionData | 정적 정의와 실행 상태 분리 | AI, 콤보, 체력, GAS, 몬스터, 캐릭터 전용 이동/애니메이션 제거 |

`GameplayTags`만 새 Runtime 의존성으로 추가한다. GameplayAbilities, GameplayTasks, UnrealEd는 추가하지 않는다.
CharacterDefinition의 현재 MW 이름은 VehicleDefinitionData다. 특정 ACharacter/CharacterMovement를 요구하지 않는다.
이동 솔루션 선정 전 차량 튜닝 형식/숫자를 고정하지 않는다. 외형별로 별도 주행 성능을 만들지 않는 기존 기획을 유지한다.

## 3. 에셋 소유권과 로딩 계약

- UMWAssetManager는 프로세스 수명의 로컬 서비스다. 서버와 클라이언트에 각자 존재하며 자동 복제되지 않는다.
- UMWAssetData의 Entries는 제작 데이터다. `InitializeCatalog`는 전체를 검사한 뒤 ID/전체 경로/라벨의 스냅샷을 만든다.
- ID는 유효하고 유일해야 한다. 다른 ID가 같은 에셋을 참조하는 별칭은 허용한다. 같은 파일명의 다른 패키지도 구분한다.
- 초기화 검사가 실패하면 이전 카탈로그와 캐시를 보존한다. 성공한 교체는 이전 캐시를 비운다.
- 초기화 뒤 원본 DataAsset을 편집해도 실행 스냅샷이 자동 변경되지 않는다. 적용하려면 명시적으로 재초기화한다.
- 동기 로딩의 PostLoad 콜백에서 카탈로그가 교체되면 이전 요청 결과는 캐시에 반영하지 않는다.
- 모든 Manager API는 게임 스레드 전용이다. 생성자·워커/물리 스레드에서 싱글턴을 조회/로드하지 않는다.
- `FindAssetPath`/`FindLoadedAsset`는 로딩하지 않는다. 미등록 ID/미로딩 값은 빈 경로/null이다.
- `LoadAssetSynchronous`는 로딩을 명시하며 실패하면 null과 로그를 남긴다. `Cast`를 이용한 템플릿 래퍼는 타입이 다르면 null이다.
- 라벨은 정확히 일치시킨다. 부모 태그 검색으로 자식을 묵시적으로 포함하지 않는다.
- `LoadAssetsByLabelSynchronous`는 모든 멤버 로딩에 성공한 뒤 캐시에 반영한다. 중간 실패 시 기존 캐시는 보존한다. 빈 라벨 집합은 성공이다.
- 캐시는 UPROPERTY/TObjectPtr로 GC가 추적한다. ID별 보관이므로 한 별칭을 해제해도 다른 별칭의 보관은 유지된다.
- `ReleaseAsset`/`ReleaseAllAssets`는 Manager의 참조만 제거한다. 다른 소비자가 참조하는 에셋을 강제로 파괴하거나 즉시 메모리 해제하지 않는다.
- 동기 로딩은 시작/모드 진입 같은 명확한 준비 지점에서 사용한다. 주행 Tick/HUD 조회에서 로드하지 않는다. 비동기 로딩은 이번 범위에 없다.
- 카탈로그 참조는 UObject 에셋이다. Pawn/BP 클래스는 VehicleDefinition의 타입이 있는 PawnClass로 지정한다. 경로 문자열을 추정해 클래스로 바꾸지 않는다.
- 경로가 유효하다는 정적 검사는 파일 존재/타입/Cook 성공의 증거가 아니다. 실제 로딩과 패키지를 별도로 검사한다.

엔진은 DefaultEngine.ini의 `AssetManagerClassName=/Script/MW.MWAssetManager`로 Manager를 생성한다.
별도 GameInstance 초기화 호출은 필요 없다.

`StartupAssetData` 미지정 상태는 에셋 제작 전의 유효한 초기 상태다. 이 경우 `HasCatalog()`는 false이며 게임 소비자는 카탈로그가 준비됐다고 가정하면 안 된다.
지정한 카탈로그의 로딩/검사가 실패하면 오류를 남기고 초기화를 중지한다.
카탈로그 초기화 이후 `AssetLabel.Preload` 멤버를 로드한다. 실패를 게임 시작 준비 완료로 처리하지 않는다.

## 4. 입력 데이터와 차량 정의 계약

UMWInputData 하나는 입력 모드 하나와 IMC 하나를 나타낸다. 현재 채택한 구분은 **Driving / SelectConstruction / PlaceConstruction**이며 각각 다른 InputData/MappingContext로 제작한다. 건설의 두 구분은 로컬 입력 하위 모드로, 서버 Phase를 추가하는 것이 아니다.

- MappingContext, 하나 이상의 InputAction, 유효하고 중복되지 않은 InputTag가 필요하다.
- 액션 조회는 정확한 태그만 사용한다. 누락/중복은 null을 반환하며 임의의 다른 액션을 선택하지 않는다.
- 입력 데이터는 매핑을 설치하거나 RPC/게임 판정을 실행하지 않는다.
- 미래 Controller는 `IsLocalController()`와 `GetLocalPlayer()`를 확인하고 LocalPlayer Subsystem에서 매핑을 설치한다.
- 모드 종료/UnPossess/EndPlay에 자신이 등록한 매핑과 바인딩을 정리한다. 전체 매핑 삭제로 다른 기능의 입력을 지우지 않는다.
- 가속처럼 유지되는 입력은 Completed와 Canceled에서 모두 해제한다.
- 아이템 사용/배치는 입력 의도를 소유 Controller의 요청 경로로 보낸다. 서버가 Phase/소유/권한을 검증한다.
- 선택/배치/주행 Context는 서로 배타적으로 설치하며 선택 클릭이 배치 Accept까지 연속 소비되지 않게 한다. 취소 액션 제거와 Enhanced Input의 `Canceled` 이벤트·모드 종료 정리는 구분한다.

운전 키 계약은 W 전방 추진, S 제동, A/D 바퀴 조향, LShift 유지형 기본 드리프트, SpaceBar 1회 사용 요청이다. `IA_Accel`은 `Input.Action.Throttle`에 연결할 가속 액션이며 예전 설계 이름 `IA_Throttle`로 파일을 바꿀 필요는 없다. 실제 IA/IMC 설정은 6.2절에서 확인했지만 `Input.Action.Brake`, `Input.Action.Drift` 네이티브 태그와 InputData 연결은 아직 남아 있다. 현재 입력 데이터 검사는 일반 누락/중복 검사이며 운전 모드의 필수 액션·값 타입·키 매핑을 자동 검사하는 것은 아니다. 상세 조합·누적·트리거·수명은 07 문서 4~5절을 따른다.

건설 선택은 Mouse2D/좌클릭, 배치는 Mouse2D/좌클릭/휠 회전을 사용한다. 취소 액션은 제외하고 줌은 후속 기능이다. 현재 네이티브 태그에는 Select/ConfirmPlacement/Cancel/Zoom이 있지만 MoveMouse와 구조물 회전을 나타내는 태그는 아직 없다. 후속 연결에서 필요한 태그를 정하고 추가한다. 남아 있는 Cancel/Zoom 태그의 선언이 해당 기능의 제작 의무를 뜻하지는 않는다. 이번 문서 정정에서 소스 태그를 삭제하거나 다른 의미로 재사용하지 않는다.

UMWVehicleDefinitionData는 VehicleId, DisplayName, 구체 PawnClass, DrivingInputData를 가진다.
VehicleId/PawnClass/주행 입력은 필수이며 입력 정의의 오류도 함께 검사한다. DisplayName은 선택 표시용이다.
서버가 승인된 정의에서 PawnClass를 선택한다. 클라이언트가 전송한 임의 클래스/경로로 스폰하지 않는다.
점수·현재 속도·보유 아이템·부스터 잔여시간은 이 에셋에 기록하지 않는다.

## 5. 실제 에셋 연결 순서

아래는 후속 제작 절차이며, 아직 없는 에셋 경로를 Config에 활성화하지 않는다.
새 .uasset 경로는 팀 Git 규칙에 따라 예약 후 한 명이 제작한다.

1. [공용 폴더 기준](<../폴더·에셋 배치 기준 및 규칙.md>)에 따라 `/Game/Input/Driving`, `/Game/Input/Construction/SelectConstruction`, `/Game/Input/Construction/PlaceConstruction`에 각 MWInputData를 만든다. 현재 같은 폴더에 제작된 IMC/InputAction을 연결하고 실제 의미에 맞는 태그를 지정한다. InputData 이름 예시는 `DA_Input_Driving`, `DA_Input_SelectConstruction`, `DA_Input_PlaceConstruction`이며 아직 제작 완료 경로가 아니다.
2. 실제 차량 Pawn이 준비되면 `/Game/Gameplay/Vehicles/Data`에 MWVehicleDefinitionData를 만들고 VehicleId, PawnClass, 주행 InputData를 지정한다.
3. MWAssetData 카탈로그를 `/Game/Data/Catalogs` 아래에 만들고 아래 ID로 실제 에셋을 등록한다. 기능 에셋 파일은 자기 폴더에 두고 카탈로그에서 참조한다.
4. 시작 때 필요한 데이터에만 `AssetLabel.Preload`를 붙인다.
5. DefaultGame.ini의 `[/Script/MW.MWAssetManager]`에 실제 경로를 지정한다. 예: `StartupAssetData=/Game/Data/Catalogs/DA_MWAssets.DA_MWAssets` (예시이며 현재 빈 설정 유지).
6. 다음 실행에서 카탈로그 초기화와 preload 결과를 확인하고, 호스트/원격에서 각각 같은 정의를 해석하는지 확인한다.
7. Windows Development Cook/패키지에서 카탈로그와 soft 참조 대상의 포함/로딩을 확인한다.

| 태그 | 현재 소스 등록 상태 | 연결 대상/후속 조치 |
|---|---|---|
| Asset.Input.Driving | 있음 | 주행 MWInputData |
| Asset.Input.Construction | 있음 | 기존 단일 건설 ID. 하나의 ID로 선택/배치 두 에셋을 동시에 등록하지 않는다. |
| Asset.Input.Construction.Select / Asset.Input.Construction.Place | **미등록·이름 제안** | 두 건설 MWInputData를 각각 조회할 별도 ID가 필요하다. 실제 이름 확정·등록과 소비 코드 연결은 후속 작업이다. |
| Asset.Vehicle.Default | 있음 | 기본 MWVehicleDefinitionData |

`PrimaryAssetTypesToScan`은 `/Game/Data`의 MWAssetData를 스캔/Cook 대상으로 등록한다.
이 설정만으로 패키지 검증을 마쳤다고 판단하지 않는다. 실제 참조된 InputAction/IMC/Pawn까지 패키지에서 확인한다.

C++ 소비 예시:

```cpp
UMWAssetManager& Assets = UMWAssetManager::Get();
// Load는 준비 단계에서만 수행한다.
const UMWVehicleDefinitionData* Definition =
	Assets.LoadAssetSynchronous<UMWVehicleDefinitionData>(MWGameplayTags::Asset_Vehicle_Default);

TArray<FText> Errors;
if (Definition && Definition->ValidateDefinition(Errors))
{
	// 미래 서버 스폰 코드는 GetPawnClass(),
	// 로컬 입력 연결 코드는 GetDrivingInputData()를 사용한다.
}

// HUD 등의 일반 조회는 이미 로드된 값만 읽는다.
const UMWInputData* Input =
	Assets.FindLoadedAsset<UMWInputData>(MWGameplayTags::Asset_Input_Driving);
```

## 6. 검증

### 6.1 공용 기반 도입 당시 검증

자동화 이름 접두사: `MW.Foundation`.

- CatalogIdentityAndLifetime: 같은 basename의 다른 경로, 별칭별 보관/해제, GC, 잘못된 카탈로그 교체 보존, 초기화 스냅샷.
- CatalogValidation: 누락 ID/참조, 무효 태그.
- InputAndVehicleDefinition: 정확한 조회, 중복/누락 입력, Pawn 기반 정의, 입력 검사 전파.
- StartupConfiguration: 실제 엔진이 MWAssetManager를 생성하고 Get이 같은 인스턴스를 반환.

2026-10-22 공용 기반 도입 당시 실행 기록 (UE 5.8.3 / Windows / MSVC 14.44 / Development):

아래는 당시 기록이며 현재 타입명 정리 이후의 재검증이나 07 차량 설계의 구현/주행 검증 결과가 아니다. 이번 기술문서 갱신에서는 게임 빌드·자동화·3인 주행을 실행하지 않았다.

| 검사 | 결과 | 범위 |
|---|---|---|
| MWEditor Win64 Development | 성공 | UHT, 새 타입/테스트 C++ 컴파일, Editor 링크 |
| MW Win64 Development | 성공 | Runtime Game 타깃 컴파일/링크, Editor 의존성 미추가 |

초기 실행에서 추상 UDataAsset으로 만든 테스트 fixture가 거부되어 구체 MWAssetData로 수정했고, 최종 실행은 모두 성공했다.
Game 타깃 링크 성공은 Cook/패키지 실행 성공을 뜻하지 않는다.
실제 제작 DataAsset의 저장/재로드/Cook, Controller 입력 등록/해제, 3인 주행·시각 확인은 4단계 검증 대상이다.

### 6.2 후속 입력 에셋 재검토 — 2026-10-22

설치된 UE 5.8.3의 `UnrealEditor-Cmd -run=pythonscript`로 저장된 `/Game/Input` 에셋 **13개(IA 10개, IMC 3개)**를 로드해 조회했다. 스크립트 실행은 성공(종료 코드 0, Commandlet 오류/경고 0)했으며 에셋 수정/저장 API는 호출하지 않았다. UE 5.8의 IMC 매핑은 deprecated `Mappings`가 아닌 `DefaultKeyMappings.Mappings`를 확인했다.

| 확인 대상 | 실제 저장 설정 | 판정/범위 |
|---|---|---|
| Driving 값 타입 | Accel/Brake/Steer=Axis1D, Drift/UseItem=Boolean | 운전 값 계약과 일치 |
| Driving 키 | W=Accel, S=Brake, A/D=Steer, LeftShift=Drift, SpaceBar=UseItem | 키 계약과 일치 |
| 조향 합산 | A 매핑 Negate, `IA_Steer` Cumulative | A/D 부호·합산 설정 일치. 실제 주행 테스트는 별도 |
| 아이템 단발 | SpaceBar **매핑에** InputTriggerPressed | 액션의 Triggers 배열이 비어 있어도 매핑에서 Pressed 적용. 후속 소비는 Triggered 한 경로 사용 |
| SelectConstruction | Mouse2D→MoveMouse Axis2D, 좌클릭→Select Boolean | 사용자 입력 의도와 일치 |
| PlaceConstruction | Mouse2D→MoveMouse Axis2D, 좌클릭→Accept Boolean, MouseWheelAxis→Turn Axis1D | Turn은 구조물 회전. 취소/줌 미제작은 현재 요구에서 누락이 아님 |
| Construction 단발 소비 | Select/Accept의 액션·매핑 Triggers 비어 있음 | Started 등 누름당 한 번 소비할 Runtime 경로는 후속 연결 대상 |
| DataAsset 연결 | `/Game`에서 MWInputData/MWAssetData/MWVehicleDefinitionData 인스턴스 미발견, StartupAssetData 미지정 | IA/IMC 제작 단계. 입력 모드 전환·태그 조회·서버 배치까지 동작 완료한 상태가 아님 |

이 검토는 저장된 에셋 설정 확인이다. 실제 커서/UI·Ghost 회전, 최종 배치 방향, 키 입력 실행, Controller 바인딩/해제, 멀티플레이·Cook/패키지는 실행 검증하지 않았다.
