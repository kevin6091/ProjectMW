## 0. 운영 전제·예산

- 팀 전체 **360인시** = A 120h + B 120h + C 120h(클라이언트 72h + TA 48h).
- **게임플레이/네트워크 워크스트림 312h** = A 120h + B 120h + C 72h. 여기에는 QA·인수인계·기술 문서·대응 여유가 포함되며 순수 코딩 312h가 아니다.
- C의 게임 작업 주별 가용 시간: **W1 8h / W2 20h / W3 18h / W4 26h**. W4의 26h는 대부분 테스트·버그·문서.
- 최우선: 3인 Listen Server → 서버 권한 트랙 배치 → 주행 → 점수/거리 차 탈락·복귀 → 라운드 확장 → 매치 종료.
- D1~D3 최소 테스트는 임시 메시/단일 차량/임시 HUD. 리소스 이전이 늦어져도 C++ 시스템은 진행한다.
- D2 첫 Development 패키지, D3 별도 프로세스/LAN 접속, D5 실제 3PC 건설·주행, D10 실제 3PC 매치, D18 릴리스 후보로 단계 검증한다. 각 작업일 예산에 포함한다.
- 현재는 기본 `MW` Runtime 모듈에서 신규 개발을 시작한다. `Source/MakeWay`로 이름을 바꾸는 작업은 하지 않는다.

## 4. 개발 계약 — 논쟁 전에 D1에 결정

### 4.1 서버 상태 흐름

1. `Lobby → TrackPlacement → HazardPlacement → Countdown → Racing → RoundResult → (TrackPlacement | MatchResult)`. 후보 선택은 TrackPlacement 내부 로컬 UI 동작으로 둔다.
2. `GameMode`는 서버에서 상태를 전환; `GameState`는 Phase/서버 기준 종료 시각/현재 라운드 복제; `PlayerState`는 준비/누적 점수. 남은 시간은 각 클라가 동일 서버 시간 기준으로 표시하며 클라 로컬 타이머를 게임 판정의 진실로 사용하지 않는다.
3. B는 Phase 변경과 기본 UI 노출 이벤트 제공. C는 화면/UI 위젯을 구독하되 서버 상태 자체를 변경하지 않음.
4. **선두와 기준 거리 이상 벌어지면 서버가 자동 탈락**시킨다. 거리 측정 방식·임계값·선두 선정·복귀 후 판정 재개 조건은 D3 계약에서 결정하고 D6~D8에 통합 검증한다. 경기 중 참가/재접속은 거부하고, 원격 이탈자는 서버 참가자 상태에서 정리한다.
5. 결승/점수 지급은 서버에서 재진입·중복 지급 방지. 기본 레이스에서 거리 차 탈락/추락/파괴된 플레이어는 **선두의 다음 유효 체크포인트 통과 시 안전하게 복귀**시키되, 전원 이탈/선두 정지 상황에는 서버 시간초과·대체 복귀 규칙을 적용한다. 복귀로 건너뛴 체크포인트 점수는 주지 않는다.
6. 점수 목표 20/35/50은 초기 가설. D8부터 매치 시간을 측정한다. 2라운드 이상 검증용 설정을 별도 두고, 종료 판정은 라운드 끝에 수행한다.
7. 공용 Phase 구조체 수신과 트랙/충돌 준비 완료를 구분한다. 서버는 제한시간 안에 리비전별 준비를 확인한 뒤 Countdown을 시작한다.

### 4.2 트랙 배치 권한

- 클라: 후보 3개 중 선택 → Ghost 로컬 미리보기 → 소유한 `PlayerController`/Component에서 서버 배치 요청.
- 서버(B): Phase/Epoch/후보/Revision/중복 검사 → 현재 마지막 소켓·간섭·스폰 영역 검사 → 동기 Spawn/등록 성공 시 1회 확정 → 구조 상태 복제. 별도 큐는 비동기 검사 시에만 도입한다.
- 다른 클라: 확정 트랙 스폰/상태로 미리보기 갱신. 복제 완료보다 빠른 Ghost 위치를 진실로 취급하지 않음.
- 동시에 두 명 배치 요청/지연 재전송이 오더라도 서버에서 중복 적용되지 않도록 건설 턴/요청 ID 관리.
- 오래된 Revision은 명시 거절하고 선택을 유지한 최신 Ghost로 재확인한다. 단일 소켓 자동 스냅을 사용하며 임의 Q/E 회전은 P0에서 제외한다.
- 정상 건설은 N개 추가한다. 타임아웃 기본 조각도 동일 검증하며 제한된 대체가 모두 실패하면 ConstructionBlocked 예외 결과로 종료한다.

### 4.3 차량과 아이템 API

- A는 속도/넉백/텔레포트 시험 API를 **D3 검증, D5 소비 계약 확정**한다. Checkpoint는 감지 후보 이벤트를 제공하고 B가 점수 유효성을 최종 검사한다.
- C는 아이템 보유 최대 1개, 사용 요청 소유권·쿨타임·유효 상태 검사, 서버 피격 판정/효과 적용.
- A는 이동 입력과 카메라를 담당, C는 아이템 입력과 HUD. 아이템 사용 결과를 클라 로컬 VFX로 표시해도 핵심 피해/넉백의 권한은 서버.
- P0 ItemComponent는 Pawn 부착. 동일 Pawn으로 복귀하며 복귀/라운드 시작·종료 때 슬롯과 임시 효과를 비운다. 채택한 이동 솔루션의 예측/물리 이력 초기화도 검증한다.

## 5. 통합·브랜치 규칙

- 작업 파일 소유자 사전 지정, 특히 `.umap`, `.uasset`은 동시 수정 금지. 공용 Map은 B만 변경, 테스트 맵은 개인별 분리.
- 하루 6h: 15분 빌드/동기화 → 2시간 15분 구현 → 15분 계약 전달 → 1시간 45분 구현/자체 테스트 → 1시간 통합 → 30분 리뷰/이슈 정리.
- PR 완료 정의: 컴파일/최소 기능 테스트/서버-클라 권한/객체 수명/로그/필요한 에셋 커밋/복구 방법/담당자 명시.
- 주중 매일 `main`의 안정 버전 보관. 통합 실패 시 반쯤 합쳐진 바이너리 에셋 대신 마지막 정상 태그에서 복구.
- **매주 마지막 날** 실사용 Gate 테스트를 진행하며, D10 매치 미완성이면 새 아이템/트랙 추가 작업을 중단.

## 7. D10/D15 범위 축소 정책

- **끝까지 P0:** 3인 Listen Server, 아케이드 이동/카메라, 트랙 서버 건설, 경합 검증, 체크포인트·복귀, 점수/라운드 확장/결과, 아이템 **최소 1종**(D10), 기본 위험 요소 최소 1종.
- **D14 마감 목표(조건부), D15 동결:** 트랙 5종, 아이템 3종(부스터/망치/기관총), 위험 2종(범퍼+정적 바리게이트 기본 후보), 보조 2종, 차량 1종, 배경 1종.
- **먼저 제거:** 두 번째 맵 → 차종 외형 추가 → 신규 아이템 P1/P2 → 특수 트랙·루프/코르크스크루 → 고급 드리프트/미니맵 → 복잡한 물리 예측 기능.

## 8. 담당별 취업 포트폴리오 증거

- A: 입력 → 네트워크 이동/보정 → 서버 위치 → 관전 클라 반영 영상, 카메라 변경 전후 사례, 충돌/복귀 디버깅 로그.

- C: 서버 아이템 획득/사용/피격 흐름, 위험 슬롯 판정, 3클라 HUD 상태와 넉백 증거, TA 도구 사용 전후 자료(별도 TA 문서).
- 팀: 3인 PC·빌드·RTT/손실 환경·장면·이탈 테스트, Git PR/코드 리뷰/릴리스 태그.

## 9. 미확정 사항과 설계 정리

- 채택할 차량 Movement 방식은 D3 기술 검증 결과에 따라 결정. Listen Server 테스트 성공을 Dedicated Server 지원으로 포장하지 않는다.
- 트랙 규격은 D2 계약, D3 변경 비용 확인. 소켓 자동 검증이 '주행 가능함'을 보장하는 것은 아니다.
- '라운드 종료 후 트랙 누적, 이전 체크포인트도 다시 점수' 방식은 35점 목표에서 예상 매치 시간과 충돌 가능: 실제 플레이테스트로 점수/상한 조정.
- 이 문서에 적힌 C++ 클래스/파일은 제안이며 실제 컴파일·실행된 코드가 아니다.
