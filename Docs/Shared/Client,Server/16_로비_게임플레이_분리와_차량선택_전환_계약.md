# 로비·게임플레이 분리와 차량 선택 전환 계약

2026-11-02 / Client + Server / 사용자 채택 설계

**현재 상태: 클래스 분리·기존 기능 이전 및 LocalIP 3프로세스 검증 완료. 차량 선택 RPC·전원 선택 대기는 아직 미구현이다. 아래 차량 선택 흐름은 후속 목표이며, 최신 사용자 지시인 “없었던 기능은 만들지 말 것”에 따라 이번 이전은 기존 즉시 테마 이동을 유지한다. 실제 이전 결과는 9절을 따른다.**

사용자 지시로 로비와 게임플레이의 GameMode·GameState·PlayerController를 분리한다. PlayerState는 공용 클래스를 사용한다. GameStart 이후에는 L_Title에서 차량 선택을 마치고, 서버가 시작 대상 전원의 선택 확정을 확인한 뒤에만 테마 레벨로 이동한다.

이 문서는 클래스 역할 분리와 앞으로 구현할 시작 흐름의 정본이다. 연결 API와 분리 이전 구현·검증 기록은 [15번 문서](15_독립_연결모듈_API와_프로젝트_연동.md)를 따른다. 이전 문서의 `GameStart → 즉시 테마 이동`은 기존 동작 기록이며 새 구현의 목표로 사용하지 않는다.

## 1. 채택한 클래스 구성

아래 클래스명으로 역할을 구분한다. 최초 설계 때는 미구현이었으며, 이후 사용자가 만든 클래스 틀에 기존 기능을 이전했다. 공용 AMWPlayerState는 유지한다.

| 역할 | L_Title의 로비 | 테마의 게임플레이 |
|---|---|---|
| 서버 규칙 | `AMWLobbyGameMode` | `AMWGameplayGameMode` |
| 복제 공용 상태 | `AMWLobbyGameState` | `AMWGameplayGameState` |
| 소유 플레이어의 입력·서버 요청 | `AMWLobbyPlayerController` | `AMWGameplayPlayerController` |
| 개인 상태 | 공용 `AMWPlayerState` | 공용 `AMWPlayerState` |

- 각 레벨의 GameMode 설정에서 GameStateClass·PlayerControllerClass·PlayerStateClass를 지정한다. 모든 테마는 같은 게임 규칙을 사용한다면 동일한 Gameplay GameMode를 사용한다.
- 기존 GameModeBase·GameStateBase 기반을 유지할 수 있다. 분리 자체를 위해 AGameMode의 별도 MatchState 시스템을 도입하지 않는다.
- Gameplay 클래스를 Lobby 클래스의 자식으로 만들어 로비 UI·Ready 규칙까지 상속하지 않는다. 공통 부모는 실제 공통 코드가 필요할 때만 둔다.
- 건설·요소 배치·카운트다운·주행은 게임플레이 월드 안의 Phase다. 단계마다 GameMode·Controller를 교체하지 않는다.
- UI 생성·제거·상태 구독·표시는 HUD 등 로컬 UI 담당 객체에 둔다. Controller에는 로컬 입력 연결과 서버 요청을 두고, 특정 WBP 생성·Refresh 의존성을 분리한다. 구체적인 HUD 클래스 수는 구현 시 필요한 범위로 정한다.
- EOS·세션 기능은 계속 MWConnection 내부에 둔다. 새 게임 클래스가 SDK나 OnlineSubsystem에 직접 접근하지 않는다.

L_Title의 Standalone 타이틀 메뉴와 Listen 로비는 같은 맵을 사용한다. 네트워크 방이 없는 타이틀 메뉴를 참가자 확정이나 차량 선택 단계로 취급하지 않는다.

## 2. 확정한 전체 흐름

```text
L_Title 로비
 → 현재 참가자 전원 Ready
 → 호스트 GameStart
 → Starting: 시작 조건 검사·참가자 고정·입장 잠금
 → VehicleSelection: 같은 L_Title에서 차량 선택
 → 시작 대상 전원의 선택을 서버가 승인·확정
 → Traveling
 → 선택한 테마로 Seamless ServerTravel
 → Gameplay GameMode·GameState·PlayerController로 진입
 → PreparingConstruction
 → TrackPlacement
 → ElementPlacement
 → PreparingRace: 차량 생성·Possess·소유 클라이언트 입력/카메라 준비
 → Countdown
 → Racing
```

**차량 선택 완료 후 추가 Ready나 두 번째 GameStart 클릭을 요구하지 않는다.** 마지막 선택 요청을 승인한 서버가 전원 확정을 확인하면 이동을 시작한다.

차량 종류를 선택하는 단계와 차량 Actor를 생성하는 단계는 다르다. 테마에 들어가기 전에 선택 ID를 확정하지만 실제 차량 생성·Possess는 건설과 요소 배치 뒤의 PreparingRace에서 수행한다.

## 3. 로비에서의 GameStart 처리

로비 Controller의 시작 요청을 받은 Lobby GameMode가 다음 순서로 처리한다.

1. 호스트 권한·로비 Phase·유효 참가자·최소 인원·전원 Ready를 검사한다.
2. 시작 대상 참가자 ID 목록을 고정하고 새 참가와 Ready 변경을 차단한다.
3. `Starting`으로 전환하고 GameInstance의 기존 입장 잠금 연동을 실행한다.
4. 온라인 잠금 완료 또는 LocalIP 준비 완료 콜백에서 참가자 목록·시작 조건을 재검사한다.
5. `VehicleSelection`으로 전환한다. 여기서 ServerTravel을 호출하지 않는다.
6. 각 소유 클라이언트의 선택 요청을 받는다.
7. 전원 선택 확정 및 참가자·테마 유효성을 확인한 뒤 `Traveling`으로 바꾸고 서버가 이동을 시작한다.

기존 `AMWGameMode::HandleStartPrepared`에서 검사를 마치자마자 실행하던 테마 이동 처리는 분리한다. 입장 잠금 완료 콜백은 차량 선택 진입을 담당하고, 테마 이동은 전원 선택 확정 후 호출하는 로비 서버 처리로 옮긴다.

입장 잠금에는 기존 MWConnection 공개 API를 사용한다. 선택 진행이나 선택 결과를 세션 Properties에 저장하지 않는다.

## 4. 차량 선택 요청과 확정 상태

선택 결과의 원본은 공용 PlayerState의 `VehicleAssetID` 하나다.

```text
선택 전: 비어 있는 VehicleAssetID
선택 후: 서버가 승인한 유효한 VehicleAssetID
```

`FMWVehicleSelection`, `bConfirmed`, 선택 Revision·선택 요청 ID를 추가하지 않는다. 게임 진행용 MatchInstanceId·RoundEpoch·PhaseRevision·RequiredChecks도 이 계약에 도입하지 않는다. 기존 연결 모듈 내부의 비동기 처리용 식별자는 별도 구현 사항이다.

클라이언트의 선택 요청 경로는 다음과 같다. 새 함수 이름은 공개 API를 구현할 때 사용할 계약 이름이며 현재 호출 가능한 함수라는 뜻이 아니다.

```text
차량 선택 UI 또는 임시 자동 선택
 → 자기 LobbyPlayerController.RequestConfirmVehicle(VehicleAssetID)
 → 소유 Controller의 Server RPC
 → LobbyGameMode의 선택 검증
 → 자기 PlayerState.VehicleAssetID에 서버 확정
 → 복제·개인 상태 변경 알림
 → 전원 선택 조건 재평가
```

UI가 없는 첫 버전에서도 각 로컬 클라이언트가 기본 차량 ID를 제출한다. 호스트도 자기 로컬 Controller의 같은 경로를 사용한다. 서버가 참가자 전원의 ID를 미리 채우는 방식으로 대체하지 않는다. 실제 선택 UI가 생기면 기본 ID 자동 제출 부분을 UI 입력으로 바꾸고 같은 요청 API를 사용한다.

서버가 검사할 조건은 다음과 같다.

- 현재 단계가 VehicleSelection이며, 요청자가 고정된 시작 대상의 유효한 참가자인가.
- 요청한 ID가 서버에서 허용한 차량인가.
- 승인 카탈로그에서 Definition을 찾고 유효성을 검사할 수 있는가.
- 생성 클래스가 실제 사용할 수 있는 Character 파생 클래스이며 필요한 입력 설정이 유효한가.
- 미선택 상태인가. 이미 같은 ID가 확정됐다면 중복 변경하지 않고, 다른 ID라면 변경을 거절한다.
- 취소도 소유 Controller가 요청한다. `VehicleSelection` 단계의 시작 대상 참가자만 서버에 확정된 자기 차량을 해제할 수 있다. 요청에 실린 기존 ID가 현재 선택과 일치할 때만 변경하고, 이미 미선택이면 중복 변경 없이 처리한다.
- 취소 승인 시 `VehicleAssetID`를 비워 복제한다. UI는 복제된 결과를 받은 뒤 선택 표시와 입력 잠금을 해제한다. `Traveling`에 진입하면 취소를 거절한다.

같은 차량을 여러 참가자가 선택할 수 있다. 태그 등록만으로 Definition·차량 클래스의 유효성을 대신하지 않는다.

## 5. 전원 확정과 이동 조건

서버의 고정된 시작 대상 참가자 목록을 기준으로 판단한다.

```text
고정된 참가자들이 계속 유효함
 AND 해당 참가자 각각의 VehicleAssetID가 서버 승인 후 확정됨
 AND 현재 단계가 VehicleSelection
 AND 테마 목적지가 유효함
 → Traveling → ServerTravel
```

클라이언트 화면에서 전원 선택으로 보이는지, UI 애니메이션이 끝났는지를 서버의 이동 조건으로 사용하지 않는다. 서버가 보유한 확정 값을 기준으로 한다.

단계 변경 알림은 각 클라이언트가 현재 상태를 다시 읽는 계기다. 알림 자체가 네트워크 전원 수신 확인이나 준비 완료 보고를 대신하지 않는다. UI가 늦게 생성되면 초기 조회로 VehicleSelection 상태와 현재 선택 결과를 반영해야 한다.

이탈 때문에 시작 대상이 달라지면 기존 시작 재검사의 엄격한 참가자 고정 정책에 맞춰 진행을 중단·정리한다. 잘못된 선택 요청은 상태를 수정하지 않고 거절한다. 필수 Definition 준비 실패나 선택 대기 제한시간 초과 등 진행 불가능 상태는 Failed·방 정리로 처리하며 준비 단계 재시도 시스템은 추가하지 않는다. 구체 제한시간 값은 구현 시 정한다.

`Traveling` 진입 후 같은 완료 이벤트가 다시 와도 이동을 중복 시작하지 않는다. 현재 Phase와 이미 확정한 값으로 중복 처리를 막는다.

## 6. 맵 이동에서 이어갈 데이터와 새로 연결할 것

| 데이터·객체 | 인계 계약 |
|---|---|
| 방·테마 설정 | 기존 서버 GameInstance에 확정 설정을 유지하고 목적지 GameMode가 Gameplay GameState에 적용 |
| 시작 대상 참가자 ID | 기존 서버 GameInstance의 StartingPlayers 활용 |
| 참가자 ID·호스트·VehicleAssetID | 공용 PlayerState의 CopyProperties·복제 계약으로 유지 |
| 로비 Ready | 로비에서 소비하는 상태. 게임플레이 준비 완료로 해석하지 않음 |
| 로비 Widget·입력 바인딩·카메라 참조 | 로비에서 정리하고 목적지의 UI·Controller에서 새로 연결 |
| 게임플레이 공용 상태 | 새 Gameplay GameState에 PreparingConstruction부터 초기화 |

GameInstance의 보관 값은 네트워크 복제 상태가 아니다. 목적지 서버가 필요한 값을 새 GameState·PlayerState에 적용하고 클라이언트로 복제한다.

Controller가 교체되는 경로를 전제로 입력·UI를 다시 연결한다. 공용 PlayerState를 사용한다는 것은 클래스 공유이며, 맵 이동 시 기존 객체의 동일성을 보장한다는 뜻이 아니다. 데이터 인계는 CopyProperties로 유지한다.

공용 PlayerState는 로비 GameState나 로비 Widget에 직접 종속되지 않도록 개인 상태 변경 알림을 정리한다. 로비 UI와 게임플레이 UI는 각자 필요한 상태를 소비한다.

## 7. 작성 시점의 실제 소스 상태

아래는 설계 채택 시점의 정적 소스 확인이다. 사용자 작업 중 상태이며 빌드·실행 검증 결과가 아니다.

| 항목 | 확인한 상태 |
|---|---|
| GameMode·GameState·Controller 역할 분리 | 기존 AMWGameMode·AMWGameState·AMWPlayerController 사용. 아직 분리 전 |
| GameStart 이후 이동 | HandleStartPrepared에서 Traveling·ServerTravel로 바로 연결됨 |
| VehicleSelection | Enum 항목·로비 안내 문구 존재. 선택 단계 진입·RPC·전원 대기는 미구현 |
| 기본 차량 태그 | `MWGameplayTags::Asset_Vehicle_Default` / `Asset.Vehicle.Default` 등록 코드 존재 |
| PlayerState.VehicleAssetID | 사용자가 멤버를 추가했고 CopyProperties에도 복사 코드 존재 |
| VehicleAssetID 초기값 | 유효한 기본 태그로 초기화됨. 빈 ID로 미선택을 표현하는 채택 계약에 맞게 조정 필요 |
| VehicleAssetID 복제 | UPROPERTY의 ReplicatedUsing 표시는 있으나 GetLifetimeReplicatedProps에 해당 필드의 DOREPLIFETIME 등록은 아직 없음 |
| 차량 ID 조회·서버 확정 API | 공개 Getter·확정 Setter·Controller 요청 RPC는 아직 없음 |
| UI·Controller | 기존 로비 Widget 생성·갱신 이벤트가 Controller에 남아 있음 |

**기본 차량 후보와 서버 승인 결과의 초기값을 구분한다.** 클라이언트가 제출할 기본 후보는 `Asset.Vehicle.Default`일 수 있지만, 서버 PlayerState의 결과를 처음부터 그 값으로 채우면 RPC를 받기 전에 전원 선택으로 판정할 수 있다. PlayerState 결과는 미선택에서 시작하고 서버 승인 경로에서만 채운다.

## 8. 구현 순서와 검증 기준

1. 로비·게임플레이 GameMode·GameState·Controller를 분리하고 레벨 및 Blueprint 기본 클래스 설정을 연결한다.
2. 기존 Controller·GameInstance·UI·PlayerState의 구체 로비 타입 캐스팅과 알림 의존성을 수정한다. 클래스 설정만 변경한 채 기존 Cast를 남기지 않는다.
3. 공용 PlayerState의 VehicleAssetID 초기 상태·조회·서버 확정·복제·맵 이동 복사를 완성한다.
4. GameStart의 준비 완료 콜백을 VehicleSelection 진입으로 변경한다.
5. 각 소유 클라이언트의 기본 ID 자동 제출 RPC와 서버 검증을 연결한다.
6. 전원 확정 이후에만 테마 이동을 실행하고 목적지에서 동일한 참가자·차량 ID를 확인한다.
7. 이후 별도 작업으로 건설 준비 보고·임시 완료 조건·차량 생성·주행 준비·카운트다운을 연결한다.

필수 인수 항목은 다음과 같다.

- 마지막 참가자가 선택하기 전에는 어느 실행 창도 테마로 이동하지 않는다.
- 호스트와 원격 참가자 모두 자기 소유 Controller 경로로 선택을 제출한다.
- 같은 ID의 중복 요청은 중복 확정·중복 이동을 만들지 않는다.
- 허용하지 않은 ID·잘못된 단계·취소 없이 다른 ID로 변경하는 요청은 거절한다. 선택 단계에서 취소한 참가자는 다시 선택할 수 있다.
- 전원 확정 후 이동은 서버에서 한 번 시작하며, 도착한 각 클라이언트에서 참가자별 차량 ID가 일치한다.
- 테마에서 Gameplay GameMode·GameState·Controller와 공용 PlayerState가 사용된다.
- 로비 UI·입력 바인딩이 게임플레이에 남거나 중복 설치되지 않는다.
- 호스트 1명·원격 2명 검증을 우선하며, 구현·빌드·실제 동기화 검증 완료를 각각 구분해 기록한다.

이번 변경은 설계 문서 반영이다. 사용자 수정 중인 Runtime 소스를 자동으로 교체하거나 위 인수 항목이 통과했다고 기록하지 않는다.

## 9. 기존 기능 이전 결과 — 2026-11-02 후속 작업

사용자의 후속 지시로 기존 기능을 직접 이전하고 한글 주석을 추가했다. **이번 범위는 역할 분리이며, 2~5절의 차량 선택 기능을 구현한 것이 아니다.**

### 9.1 실제 클래스와 이전한 책임

| 목적지 | 이전 내용 |
|---|---|
| `System/GameMode/MWLobbyGameMode` | 방 초기화, PreLogin/PostLogin, 참가자 ID·호스트·Ready 초기화, Ready 검증, 시작 권한·대상 고정, 입장 잠금 완료 재검사, 테마 이동, 시작 실패 정리 |
| `System/GameMode/MWGameplayGameMode` | 기존 테마 초기화 분기, 방 설정·정원 적용, PreparingConstruction 진입, 신규 입장 차단, 자동 Pawn 생성 방지 |
| `System/GameState/MWLobbyGameState` | 방 설정·로비 Phase 복제, 참가자 추가/제거 알림, Ready·시작 가능 조건 조회 |

| 공용 `MWPlayerState` | 기존 개인 데이터·CopyProperties 유지. 특정 GameState 호출 대신 OnPlayerStateChanged 알림 사용 |

최초 이전 직후에는 기존 `AMWGameMode`, `AMWGameState`, `AMWPlayerController`와 Controller BP 이벤트를 호환용으로 유지했다. 이후 사용자 정리 지시에 따라 참조 검사를 마치고 이 클래스들과 기존 BP를 삭제했다. 현재 남은 클래스와 삭제 검증은 9.4절을 따른다.

타이틀 Root Widget의 생성·정리는 기존 L_Title Level Blueprint를 유지한다. 로비 Widget만 새 HUD가 소유하며, Frontend 시각 에셋을 새로 만들거나 교체하지 않았다. MWRoomLobbyWidget의 GameInstance 세션 상태·오류 구독도 유지한다.

GameInstance에서는 기존 GameMode/GameState Cast를 새 역할에 맞게 교체했다. 초기화는 각 GameMode의 InitGameState/StartPlay에서 수행하며, 연결 모듈의 월드 준비 알림에서 GameMode를 직접 초기화하지 않는다. MWConnection 플러그인 구현·공개 API는 수정하지 않았다.

### 9.2 레벨과 Blueprint 연결

| 레벨 | GameMode | GameState | Controller | PlayerState |
|---|---|---|---|---|
| L_Title | BP_MWLobbyGameMode | MWLobbyGameState | MWLobbyPlayerController | MWPlayerState |
| L_Dev_Default | BP_MWGameplayGameMode | MWGameplayGameState | MWGameplayPlayerController | MWPlayerState |

두 GameMode의 DefaultPawnClass는 None, Seamless Travel은 켬이다. Lobby HUDClass는 MWLobbyHUD, Gameplay HUDClass는 기본 HUD다.

현재 실제 시작 흐름은 다음과 같다.

```text

→ Traveling → 테마 이동 → PreparingConstruction
```

차량 선택 RPC·자동 기본 ID 제출·전원 선택 대기·건설 완료 조건·차량 생성·주행·카운트다운 실행은 추가하지 않았다. VehicleAssetID는 사용자가 작성한 빈 초기값·CopyProperties 코드를 보존했으며, Getter/확정 Setter/추가 복제 등록도 이번 이전에서 구현하지 않았다.

### 9.3 실제 검증과 한계

- 임시 검증 코드를 제거한 최종 MWEditor Win64 Development·MW Win64 Development 빌드 모두 통과했다.
- 두 레벨을 실제 로드해 GameMode Override를 저장하고, 두 GameMode BP의 GameState/Controller/PlayerState/HUD 기본값을 확인했다.
- 관련 Blueprint 11개 컴파일 통과: 기존/새 GameMode 3개, 기존 Controller 1개, 로비 UI 7개.
- LocalIP 독립 3프로세스에서 실제 생성·주소 참가·각 소유 Controller의 Ready RPC·호스트 시작 RPC를 사용했다. 상태를 직접 주입하지 않았다.
- 세 실행 모두 참가자 3명·서로 다른 ID·호스트 1명·전원 Ready·로비 Widget 1개·인원 표시 3/3을 확인했다.
- 세 실행 모두 테마에서 GameplayGameState/GameplayPlayerController·PreparingConstruction·기존 ID/Ready 유지·로비 Widget 0개·커서 숨김·Pawn 미생성을 확인했다.
- 참가자 둘의 종료·타이틀 복귀, 호스트 종료·복귀·재생성·재종료를 확인했다.
- 최초 실행에서는 마지막 클라이언트의 참가자 복제 전에 자동 시작해 로비 화면 검증을 마치지 못했다. 검증 실행을 30FPS 및 시작 전 5초 관찰로 조정한 뒤 세 실행 모두 통과했다. 게임 로직에 클라이언트 UI 수신 대기 조건을 추가하지 않았다.

- 기존 DA_Driving_InputData의 Input.Action.Drive.Reverse 태그 경고는 이번 범위에서 수정하지 않았다.
- 검증 전용 C++와 그 오브젝트·진단 파일, 임시 Python·로그·결과 파일을 삭제했다. 최종 Editor DLL과 게임 EXE에 임시 검증 명령이 남지 않은 것도 확인했다.

사용자 지시로 다음 파일을 삭제했다. 차량 선택 등 새로운 게임 기능은 추가하지 않았다.
