# Engineering 개발 전 필독 가이드

**적용:** ProjectMW의 Client·Server·TA 코드/도구 작업과 관련 설계·리뷰.
**기준:** UE 5.8.3, 기존 `MW` 모듈, 3인 Listen Server 우선. 이 문서는 구현 완료를 뜻하지 않는다.

이 문서는 에이전트가 설계하고 검증하는 방법을 정한다. 게임 규칙은 [기획](../Shared/MakeWay_기획최종안.md), 기능 계약은 [개발명세](../Shared/Client,Server/MakeWay_클라이언트_개발명세서_v1.0.md), 일별 일정은 [마일스톤](../Shared/Client,Server/02_클라이언트_마일스톤_4주.md)이 원본이다. 분야별 필독 범위는 [작업 분류 스킬](../../.agents/skills/mw-task-routing/SKILL.md)을 따른다.

## 1. 적용 강도와 판단 순서

- **필수:** 게임 의도·권한·데이터 무결성·수명·종료 경로·검증 사실을 지키는 기준이다.
- **기본:** 특별한 근거가 없으면 적용한다. 기존 코드나 측정 결과에 따라 다른 선택을 하면 이유를 남긴다.
- **조건부:** RPC, 비동기 처리, 물리 예측, 데이터 변경처럼 해당 작업에서 사용하는 항목에 적용한다.
- 우선순위는 **요구 동작의 정확성 → 상태/수명 안정성 → 읽고 변경하기 쉬운 구조 → 검증 가능한 성능**이다. 일정·성능 최적화가 게임의 핵심 규칙을 무단으로 없애는 근거가 되지 않는다.
- 단순 변경은 짧게 판단하고 바로 작업한다. 모든 작업에 설계서·회의·승인·자동화 테스트를 새로 요구하지 않는다. 복잡한 변경만 아래 계약과 근거를 별도 기록한다.

## 2. 기획 의도와 완료 조건부터 고정한다 — 필수

1. 사용자에게 보이는 변경 전/후 동작을 한두 문장으로 적는다. 관련 요구 ID와 명세 절을 찾는다.
2. 성공 조건뿐 아니라 실패했을 때의 화면·상태·다음 행동도 정한다. “컴파일 성공”, “클래스 추가”만으로 기능 완료를 정의하지 않는다.
3. 이번 작업에 포함할 범위와 후속 과제를 구분한다. 기존 동작과 호환되어야 하는 조건도 확인한다.
4. **기획 규칙, 구현 방법, 작업 우선순위를 구분한다.** 더 단순한 구현을 택할 수 있어도 규칙 자체의 삭제·변경이 자동으로 허용되는 것은 아니다. 예를 들어 선두와의 거리 차 자동 탈락은 게임 규칙이고, 거리 계산 방법은 설계 선택이다.
5. 문서 충돌은 현재 사용자 지시와 실제 합의 기록을 확인해 해결한다. 요구가 결정되지 않았다면 미정 항목과 영향을 기록하고, 그 결정에 의존하지 않는 작업을 계속한다. 미정 수치를 확정값처럼 넣지 않는다.

## 3. 수정 전에 실제 구현과 영향 범위를 조사한다 — 필수

- Git 작업은 [3인 팀 Git 공통 규칙](../Shared/GIT_COLLABORATION_GUIDE.md)을 적용한다. 짧은 작업 브랜치·독립 리뷰·최신 main 검증·순차 병합이 기본이다.
- 실제 저장소 루트·브랜치·작업 변경 사항을 확인한다. 기존 사용자 변경과 이번 변경을 구분하고 임의로 되돌리지 않는다.
- 문서의 제안 클래스/경로와 현재 소스를 대조한다. 존재하지 않는 시스템을 구현된 전제로 사용하거나 기존 코드가 있다고 가정해 마이그레이션을 시작하지 않는다.
- `rg` 등으로 관련 타입·호출자·수신자·복제 필드·BP 노출·설정·에셋 참조를 확인한다. 같은 책임의 구현이 있으면 재사용 또는 확장 가능성을 먼저 검토한다.
- 입력/이벤트 → 권한 검사 → 상태 변경 → 복제 → UI/효과까지 이번 작업의 경로를 추적한다. 버그는 재현 조건과 원인 경로를 확인하고 증상을 숨기는 우회부터 추가하지 않는다.
- 새 API는 설치 엔진의 헤더/소스·활성 플러그인·Build.cs와 공식 문서로 확인한다. 다른 UE 버전의 예제나 블로그 코드를 그대로 사용할 수 있다고 가정하지 않는다.

## 4. 책임·상태 소유자·수명을 먼저 정한다 — 필수

각 기능에 **최종 결정을 내리는 곳, 상태를 보관하는 곳, 표시하는 곳, 정리하는 곳**을 정한다. 하나의 상태를 여러 클래스에서 서로 수정하지 않게 한다. 모든 기능을 단일 Manager에 모으라는 의미는 아니다.

| 대상 | 기본 배치 기준 | 피해야 할 혼동 |
|---|---|---|
| GameMode | 서버 경기 규칙·전환·최종 판정 | 클라이언트 UI의 조회 대상 |
| GameState / PlayerState | 공용 경기 상태 / 플레이어별 경기 상태의 복제 | Widget과 별도 점수 원본 유지 |
| PlayerController | 소유자 요청·로컬 입력/화면 연결 | 다른 클라이언트의 Controller 존재 가정 |
| Pawn / Component | 차량과 수명이 같은 기능·상태 | 차량 소멸 후에도 필요한 기록의 유일 보관처 |
| Widget | 현재 상태 표시·사용자 의도 전달 | 점수·배치·탈락의 최종 판정 |
| Subsystem | World·GameInstance·LocalPlayer 등 필요한 수명에 맞는 서비스 | 자동 복제되는 전역 게임 규칙 객체로 취급 |

현재 명세의 `GameModeBase/GameStateBase`와 Phase 계약을 우선한다. 새 Component·Interface·Subsystem·모듈은 독립 수명, 실제 교체 지점, 별도 의존성 또는 반복되는 책임이 있을 때 도입한다. 미래 확장 가능성만으로 계층을 추가하지 않는다.

규칙이 UI/에셋 구현을 직접 호출하는 순환 의존을 피한다. 표시 코드는 상태와 의미 있는 이벤트를 소비한다. 같은 값을 복제·UI 캐시·물리 상태에 보관해야 하면 원본, 갱신자, 재동기화 방법을 밝힌다. Subsystem 수명 기준은 [Epic 문서](https://dev.epicgames.com/documentation/en-us/unreal-engine/programming-subsystems-in-unreal-engine)를 참고한다.

## 5. 공유 API·데이터 계약을 명시한다 — 조건부

다른 분야·객체·프로세스가 소비하는 계약은 최소한 다음을 답해야 한다. 기존 계약이 충분하면 중복 문서를 만들지 않는다.

| 항목 | 기록할 내용 |
|---|---|
| 의미 / 소유자 | 무엇을 요청·조회·변경하는지, 호출자·최종 판정자·소비자 |
| 입력 / 출력 | 타입, ID 범위, 필수/옵션, 무효값, 성공/거절 결과와 사유 |
| 단위 / 좌표 | cm·초 등 단위, Local/World, 기준 Transform, 방향·범위 |
| 전제 / 수명 | Phase/Epoch, 필요한 객체·로드 상태, 소유권, 유효 기간 |
| 실행 / 순서 | 게임·물리·워커 스레드, 동기/비동기, 실제 순서 보장 |
| 재요청 / 중복 | 요청 ID 범위, 이미 처리한 요청의 응답, 부작용 중복 방지 |
| 취소 / 실패 | 시간초과, 이탈·파괴·Phase 변경, 부분 성공 정리와 후속 행동 |
| 호환 / 검증 | 호출자·BP·데이터 영향, 변경 전후 검사와 재현 방법 |

`bool` 하나로 거절 원인을 구분하기 어렵다면 명시적인 결과 enum/구조체를 사용한다. 정상 거절을 예외 상황과 섞지 않는다. 모든 로컬 함수에 네트워크용 ID/리비전을 덧붙이는 식으로 확대하지 않는다.

## 6. 상태 전환과 실패 시 종료 경로를 설계한다 — 필수

- 상태별 허용 입력·진입·종료 조건과 변경 후 반드시 성립할 조건을 정한다. 함께 성립해야 하는 조건은 코드와 테스트에서 관찰 가능하게 한다.
- 여러 bool 조합으로 불가능한 상태가 생기면 enum/상태 구조로 표현한다. 이미 있는 Phase와 별도 FSM을 중복 운영하지 않는다.
- 검증 → 필요한 리소스 준비 → 부작용 확정 순서를 정한다. 실패하면 스폰·등록·대기 표시·예약을 정리한다. 비동기라면 완료 시점에도 Phase·Epoch·대상 유효성을 다시 확인한다.
- 한 번 확정된 점수·픽업·슬롯 소모가 중복 콜백/요청으로 재적용되지 않게 한다. 네트워크 전송 자체가 한 번만 일어난다고 가정하지 않는다.
- 외부 응답·참가자 준비·복귀·비동기 로드를 기다리면 제한시간과 취소/대체/예외 종료를 정한다. 후보가 모두 실패했을 때 무한 재시도하지 않는다.
- 다음 라운드·재경기·맵 전환에서 초기화할 상태와 남길 상태를 구분한다. 정상 완료와 취소가 같은 자원을 서로 두 번 정리하지 않게 한다.

## 7. Listen Server와 복제 계약을 확인한다 — 조건부

- Client 입력은 요청이며, 서버가 규칙에 따라 결과를 확정한다. UI/로컬 타이머/클라이언트 적중 보고만으로 결과를 결정하지 않는다.
- Server RPC는 실제 owning connection 경로를 확인한다. 서버에서 스폰했다는 이유만으로 아무 클라이언트나 그 Actor에 요청할 수 있다고 가정하지 않는다.
- 지속 상태와 일시적 연출을 구분한다. HUD는 생성 시 현재 상태를 반영하고 변경을 구독한다. 이벤트를 놓쳐도 현재 상태를 다시 표시할 수 있게 한다.
- 서로 다른 Actor/RPC 또는 RepNotify 호출의 상대 순서를 가정하지 않는다. 관련 상태를 묶어도 다른 Actor·에셋·충돌의 준비까지 보장되지는 않는다. 필요한 ID/리비전과 실제 준비 조건을 확인한다. [복제 실행 순서](https://dev.epicgames.com/documentation/en-us/unreal-engine/replicated-object-execution-order-in-unreal-engine)
- 호스트의 권한 처리 후 표시 갱신과 원격 클라이언트의 수신 후 표시 갱신을 모두 확인한다. C++ 서버 측 필드 대입만으로 OnRep 표시가 실행된다고 가정하지 않는다. 공용 갱신 함수를 사용하면 중복 호출에도 안전하게 한다.
- Reliable 여부는 유실 시 영향·빈도·재전송 비용으로 정한다. 매 Tick 위치나 연출을 Reliable RPC로 보내는 방식을 기본으로 삼지 않는다.
- `WithValidation`의 `_Validate` 실패는 호출 클라이언트의 연결 종료를 일으킨다. stale 리비전·이미 사용한 아이템 등 예상 가능한 게임 규칙 거절을 무조건 연결 종료로 처리하지 않는다. [RPC 공식 문서](https://dev.epicgames.com/documentation/en-us/unreal-engine/remote-procedure-calls-in-unreal-engine)
- 차량의 가속·넉백·텔레포트는 채택한 이동 솔루션의 예측/보정 계약을 따른다. 물리 재시뮬레이션에서 점수·아이템·FX 부작용이 반복되지 않게 한다.

## 8. UObject·비동기·구독의 수명을 닫는다 — 조건부

- 참조가 대상을 살아 있게 해야 하는지, 파괴되면 무효가 되어야 하는지, 필요할 때 로드할 자산인지 먼저 판단한다.
- GC가 추적해야 하는 UObject 멤버는 적절한 `UPROPERTY`와 `TObjectPtr`, 비소유 캐시는 `TWeakObjectPtr`, 지연 자산은 `TSoftObjectPtr` 등을 목적에 맞게 선택한다. Raw Pointer나 모든 포인터를 일괄 금지하는 규칙으로 대체하지 않는다. [Object Pointers](https://dev.epicgames.com/documentation/en-us/unreal-engine/object-pointers-in-unreal-engine)
- 생성자·초기화·BeginPlay·Possess/UnPossess·위젯 재생성·EndPlay 중 실제 유효 시점을 확인한다. 다른 Actor의 BeginPlay 순서와 임의 Delay에 의존하지 않는다.
- Timer·Delegate·비동기 핸들·입력 매핑은 등록 위치와 해제/취소 위치를 짝지어 관리한다. 재구독하면 이전 등록을 정리하고, 파괴된 소유자로 콜백이 들어오지 않게 한다.
- 지연 실행 람다가 잡은 UObject/`this`의 수명을 확인한다. weak 참조를 쓰더라도 콜백 실행 시 유효성과 최신 작업 ID/Phase를 확인한다.
- 워커/물리 스레드에는 필요한 값의 스냅샷을 전달한다. 해당 API의 지원이 확인되지 않은 UObject·UI·월드 변경은 게임 스레드로 전달하고 재검증한다. 이미 취소된 작업의 결과를 최신 상태에 덮어쓰지 않는다.

## 9. 읽기 쉬운 코드와 오류 처리를 유지한다 — 기본

- 기존 저장소 스타일과 [Epic C++ Coding Standard](https://dev.epicgames.com/documentation/en-us/unreal-engine/epic-cplusplus-coding-standard-for-unreal-engine)를 기준으로 이름·접두사·타입·include를 일관되게 쓴다. 주변 코드 전체를 무관하게 재포맷하지 않는다.
- 이름으로 대상·행위·조건이 드러나게 한다. `Data`, `Manager`, `Process` 같은 이름만으로 책임을 감추지 않는다. 공개 값은 필요한 경우 단위/좌표계도 드러낸다.
- 함수는 한 가지 의미 있는 동작을 담당하게 하고, 조회와 부작용을 구분한다. 읽는 함수가 몰래 점수/상태를 바꾸거나 자산을 동기 로드하지 않게 한다.
- 변경하지 않는 값은 `const`, override는 `override` 등으로 의도를 드러낸다. 반복되는 규칙 값은 의미 있는 설정/상수로 모으되, 일회성 표현까지 무조건 추상화하지 않는다.
- API는 필요한 부분만 공개한다. UPROPERTY/UFUNCTION의 노출·편집·복제 지정은 실제 소비 목적에 맞춘다. 외부가 내부 배열/상태를 직접 수정하며 불변 조건을 우회하지 않게 한다.
- 헤더 의존성을 줄이고 필요한 include/모듈 의존성을 명시한다. Public/Private Dependency는 공개 헤더의 실제 사용을 기준으로 선택한다. Unity Build나 PCH의 우연한 간접 include에 기대지 않는다.
- 정상적으로 없을 수 있는 값은 명시 처리하고, 필수 의존성이 빠졌으면 원인·대상과 안전한 실패 결과를 남긴다. 모든 오류를 `if (!X) return;`로 숨기거나, 외부 입력에 무조건 `check`를 걸지 않는다.
- 주석은 왜 이 제약이 필요한지, 엔진 제약·단위·권한·순서·대체안의 이유를 설명한다. 코드와 같은 말을 반복하는 주석과 해결 시점 없는 TODO를 늘리지 않는다.
- 함수 길이·클래스 개수·상속 깊이에 임의의 숫자를 일괄 강제하지 않는다. 책임 혼합, 중복 변경, 깊은 분기, 설명하기 어려운 의존 관계가 실제 분리 기준이다.

## 10. C++·Blueprint·데이터·Editor 경계를 지킨다 — 조건부

- 안정적인 공용 계약·규칙과 반복 조정하는 수치·배치·연출을 구분한다. C++/Blueprint 중 무엇을 쓰는지는 성능·편집 주체·검증·리뷰 가능성으로 판단한다. 어느 쪽도 일괄 강제하지 않는다. [Blueprint와 C++](https://dev.epicgames.com/documentation/unreal-engine/coding-in-unreal-engine-blueprint-vs-cplusplus?lang=en-US)
- Widget/BP가 규칙 내부 변수에 직접 접근해 결과를 덮어쓰게 하지 않는다. BP에는 목적이 드러나는 작은 API를 제공한다.
- 밸런스 값·후보 정의는 기존 DataAsset/설정 경로를 활용한다. 문자열 경로·배열 순서만으로 영구 식별하지 않는다. enum/구조체/프로퍼티 이름을 바꾸면 BP·직렬화 데이터·설정·리다이렉트 필요성을 확인한다.
- Soft Reference를 사용하면 로드 완료·취소·실패와 Cook 포함 여부를 함께 확인한다. Editor에서 보인다는 이유로 패키지에서도 로드된다고 간주하지 않는다.
- Runtime에 Editor 전용 의존성이 새지 않게 한다. TA 자동 수정은 재실행 영향·Undo/Transaction·변경 에셋 범위·실패 시 보존을 설계한다.
- 데이터 생산자·소비자와 필수/옵션 필드를 맞춘다. 반복 검사가 이득인 항목은 기존 Data Validation을 우선 검토하되, 정적 Validator 통과를 실제 차량 주행/월드 충돌 통과와 동일시하지 않는다. [Data Validation](https://dev.epicgames.com/documentation/en-us/unreal-engine/data-validation-in-unreal-engine)

## 11. 작업 효율과 성능을 근거로 개선한다 — 기본

- 작업은 동작이 확인되는 작은 단위로 연결한다. 예: 입력 → 서버 승인 → 상태/화면 → 실패 처리까지 최소 흐름을 먼저 완성하고 콘텐츠 수를 늘린다.
- 불확실한 엔진/플러그인 기능은 작은 시험으로 핵심 위험을 먼저 확인한다. 후보·판정 기준·종료 시점을 정하고, 검증되지 않은 실험을 완료된 기반 구조로 숨기지 않는다.
- 기존 함수/기능을 재사용하되 책임이 다른 기능을 억지로 합치지 않는다. 리팩터링은 이번 문제의 원인 제거와 변경 안전성에 필요한 범위로 한다.
- 새 Tick·반복 월드 검색·고빈도 UMG 바인딩·불필요한 복제·동기 로드를 추가하면 빈도와 필요성을 확인한다. 적합하면 이벤트/등록 기반으로 전환하되 Tick 자체를 무조건 금지하지 않는다.
- 최적화는 같은 빌드·장면·인원·트랙 수·장비에서 변경 전/후를 비교한다. 프레임 시간, Game/Physics/Render Thread, 메모리·로딩·네트워크 중 실제 병목을 찾는다. [Unreal Insights](https://dev.epicgames.com/documentation/en-us/unreal-engine/unreal-insights-in-unreal-engine)
- 근거 없는 프레임/대역폭 보장, 조기 풀링·범용 프레임워크 도입, 성능을 이유로 한 핵심 규칙 삭제를 피한다. 위험·예산·대안은 기록하고 미확정 예산은 미정으로 표시한다.
- 같은 코드와 조건으로 이미 통과한 검사를 이유 없이 반복하지 않는다. 변경·실패·새 의심이 생기면 필요한 범위로 다시 검증한다.

## 12. 변경 위험에 맞는 검증을 선택한다 — 필수

| 변경 | 최소한 확인할 내용 | 필요할 때 확대할 검증 |
|---|---|---|
| 문서/주석 | 요구 일치, 참조 경로, 모순·구형 규칙, diff | 게임 빌드 불필요 |
| 로컬 UI/입력 | 초기 상태, 갱신, 열기/닫기·재생성, 입력 모드 | 소유자/호스트/원격이 다르면 각각 확인 |
| 규칙/RPC/복제 | 정상·거절·중복·오래된 요청·Phase 변경, 서버/클라 일치 | 지연·손실·동시 요청·이탈, 3인 Listen Server |
| 상태/비동기/수명 | 생성·성공·취소·시간초과·파괴·재시작, 늦은 콜백 | 맵 이동·재경기·반복 실행 |
| 차량/물리/효과 | 조작·충돌·외부 힘·복귀·보정 후 상태 | 호스트/원격·지연·동시 충돌·재시뮬레이션 |
| C++/리플렉션/모듈 | 관련 타깃 컴파일, BP 연결·기본값·의존성 | Editor 종료 후 정상 빌드/재실행, Game 타깃·Cook/패키지 |
| 데이터/에셋 계약 | 생산자·소비자·참조·유효 데이터와 실패 데이터 | Validator, 실제 런타임·패키지 로드 |

- 먼저 “어떤 결함을 찾을 것인가”를 정한다. 순수 규칙·상태 전환·재발 위험이 큰 로직은 자동화 테스트 후보이고, 구현을 그대로 따라 쓰는 테스트와 사소한 변경의 테스트 파일 양산은 피한다.
- 엔진 자동화가 필요하면 기존 [Automation Test Framework](https://dev.epicgames.com/documentation/en-us/unreal-engine/automation-test-framework-in-unreal-engine)와 프로젝트의 테스트 구조를 확인한다. 테스트를 위해 무관한 프레임워크를 먼저 도입하지 않는다.
- PIE 3창·별도 프로세스·실제 3PC 패키지는 서로 다른 증거다. 실행한 조건만 통과로 기록한다. 전체 매치/릴리스 게이트는 마일스톤의 실제 3PC 기준을 따른다.
- 컴파일·수동 확인·멀티플레이·Cook/패키지는 각기 다른 결함을 찾는다. Live Coding 성공이나 Editor 한 화면 실행으로 나머지까지 성공했다고 보고하지 않는다.

## 13. 리뷰·완료·인계 기준 — 필수

- 요구 동작과 관련 실패 경로가 연결되었고, 임시 스텁/비활성 분기로 성공을 가장하지 않는다.
- 상태 원본·권한·초기화·취소/해제·재경기 경로가 설명 가능하다. 새 API의 모든 생산자/소비자와 BP/데이터 영향이 확인되었다.
- diff를 읽어 무관한 변경·실험용 코드·과도한 로그·에셋 일괄 재저장·비밀값 포함 여부를 확인한다. 기존 사용자 작업을 보존한다.
- 로그는 필요에 맞는 카테고리/레벨과 원인·대상·Phase/Epoch/RequestId 등을 남긴다. 고빈도 로그는 제한하고, 재현 없이 볼 수 없는 정보만으로 오류를 설명하지 않는다.
- 실제로 실행한 검증의 조건·결과와 실행하지 못한 검증·남은 문제를 구분한다. 미검증을 완료로 올리지 않는다.
- 규칙/계약을 바꿨으면 원본 문서와 직접 영향받는 일정·인수 조건을 같이 갱신한다. Git 커밋/푸시/병합은 요청 범위와 공통 Git 규칙을 적용하고, 고위험 변경의 두 팀원 검토 기준을 지킨다.
- 최종 보고는 변경 이유·사용자에게 달라진 동작·주요 파일·검증·남은 제한을 담는다. 사소한 내부 작업을 시간 순서대로 나열하지 않는다.

## 14. 작업 시작 메모 예시

아래는 별도 승인 양식이 아닌 설계 누락을 찾는 예시다. 작은 작업은 작업 안내나 기존 이슈에 짧게 적으면 충분하다.

```text
목표: 선두와 거리 기준 이상 벌어진 차량은 기본 레이스에서 탈락 대기 후 복귀한다.
근거: 기획 3.4·7절 및 현재 사용자 지시. 구체 거리/측정 방식은 아직 미정.
영향: Server 판정 + Client 상태/HUD + 기존 복귀·점수 경로.
원본/책임: 서버 레이스 규칙이 선두·거리·대상 상태를 판정. UI는 표시.
전환: Racing/Active → PendingRespawn → 기존 안전 복귀 → Active.
보존: 건너뛴 체크포인트 점수 미지급. 서든데스는 기존 복귀 금지 규칙 적용.
위험: 선두 교체, 지연/보정, 곡선 구간, 전원 이탈, 복귀 직후 재탈락.
선행 결정: 거리 지표·임계값·평가/재개 조건을 정하고 관련 데이터 필요성을 확인.
검증: 경계값·중복 판정·다음 체크포인트 복귀·점수·호스트/원격 일치.
```

## 15. 가이드 유지 규칙과 근거의 적용 범위

이 파일에는 여러 기능에 재사용할 판단 기준을 둔다. 구체 게임 수치·20일 일정·개별 API 전체를 복사하지 않는다. 기능 계약은 개발명세, 분야별 고유 기준은 Client/Server 규칙에 남겨 중복 수정을 줄인다.

공식 자료의 엔진 동작과 이 프로젝트의 설계 선택은 구분한다. 위 링크는 2026-10-22 확인한 Epic 문서이며, 구현 시 설치된 5.8.3 헤더·소스·플러그인 설정과 다시 대조한다. 문서 확인만으로 실제 프로젝트 컴파일/런타임 검증을 대신하지 않는다.
