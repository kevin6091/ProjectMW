# ProjectMW 트랙 배치 알고리즘 설계 v0.1

작성일: 2026-10-28. 분야: Server + Client + Art/TA.

상태: 검토용 신규 설계. 코드·에셋·프로젝트 원본 문서를 변경하지 않았으며 구현·주행·네트워크 검증 결과가 아니다. Make Way 내부 알고리즘의 복원본이 아니다.

## 1. 목표와 전제

플레이어는 조각을 선택하고 두 연결 방향 중 하나를 확인한 뒤 설치한다. 시스템은 현재 코스 끝에 정확히 연결하고, 불가능하면 원인과 문제 위치를 보여준다.

- 단일 경로·끝점 하나에 추가한다. 분기는 이번 범위에 포함하지 않는다.
- 두 끝 A/B는 모두 입구·출구가 될 수 있다. 방향은 A→B와 B→A뿐이다.
- 자유 Yaw/Pitch/Roll, 런타임 미러링, 음수·비균일 스케일은 사용하지 않는다. 배치 Scale은 1이다.
- 높이는 조각의 형상과 소켓 연결로 결정된다. 별도의 자유 높이 조작을 추가하지 않는다.
- 직선·커브·S자·검증된 완만한 경사부터 지원한다. 루프·동적 다리·점프 착지의 안전 보장은 별도 범위다.
- 서버가 배치 결과를 확정한다. 클라이언트의 Ghost는 예상 결과다.
- 고도·연결·간섭·도착 구간 공간 확보를 독립 판정으로 둔다.
- U턴, 누적 회전각, 시작 방향의 반대쪽이라는 이유만으로 거절하지 않는다.
- 모든 확정 조각은 그 끝에서 도착 구간을 생성할 수 있어야 한다. 다음 조각을 무한히 이어갈 수 있다는 보장은 하지 않는다.

기존 18초 제한, 정상 라운드의 참가자당 1조각, stale 요청 명시 거절, 제한된 대체 실패 시 ConstructionBlocked, 실제 코스 준비 확인 뒤 출발 계약은 유지한다. 이것은 타이머·점수 정책을 바꾸는 설계가 아니다.

## 2. 현재 프로젝트와 기존 문서의 차이

현재 Source/MW에는 차량·공용 데이터·프론트엔드 코드가 있고 TrackManager/TrackPiece/배치 판정 소스는 확인되지 않았다. 현재 작업 브랜치는 feature/vehicle-movement다. 따라서 이 문서는 별도 검토 자료로 두며 차량 작업에 변경을 섞지 않는다.

참고 원본:

- Docs/Shared/MakeWay_기획최종안.md: 경기 루프·건설·서버 권한.
- Docs/Shared/Client,Server/MakeWay_클라이언트_개발명세서_v1.0.md: 4절 배치, 5절 체크포인트, 복제·준비 확인.
- Docs/Shared/TA/MakeWay_TA_개발명세서_v1.0.md: 2절 데이터, 3절 정적 검증, 5절 주행 충돌과 Footprint 분리.
- Docs/Engineering/DEVELOPMENT_GUIDE.md 및 분야별 WORK_RULES.md.

이번 사용자 지시의 양방향 연결·두 방향 원칙을 기존 문서의 고정 In/Out 기본안보다 우선한다. 방향 선택 요청 인자, 양방향 메타데이터, 자동 도착 도로와 예약 공간은 기존 계약에 추가할 제안이다. 기존 문서에서 회전 연계가 미정이라는 사실을 구현 완료로 해석하지 않는다.

기존 문서의 UE 5.8.3 표기와 최근 프론트엔드 문서의 검증 UE 5.8.4 표기가 함께 존재한다. 이번 설계는 특정 패치 API에 의존하지 않으며 구현 착수 시 실제 설치 엔진을 재확인한다.

## 3. 트랙 제작 데이터

아래 이름은 의미를 설명하는 제안이며 새 C++ 타입의 구현 완료를 뜻하지 않는다.

| 데이터 | 의미 |
|---|---|
| PieceId / DefinitionVersion | 서버 승인 카탈로그의 안정 ID와 데이터 버전 |
| Mesh / Collision | 시각 메시와 실제 주행·장애물 충돌 |
| PortA / PortB | 로컬 연결 Transform, 폭·연결 규격 |
| SolidFootprints[] | 도로 두께·난간 등 설치 공간을 차지하는 작은 방향성 박스들 |
| DriveClearance[] | 차량이 지나갈 수 있어야 하는 공간의 작은 방향성 박스들 |
| DriveHeightGeometry | 고도 범위 검사에 사용할 도로 영역. 단순 박스로 충분하면 SolidFootprints와 공유 |
| CenterlineSamples[] | A→B 순서의 위치·접선·표면 Up·누적거리. 곡선은 실제 형상을 따라 샘플링 |
| JoinCollarA/B | 접합부의 아주 짧은 영역과 그 영역에 속한 검사 Shape 식별 |
| DirectionalMetadata[2] | 방향별 체크포인트·안전 복귀·진행 방향 영향을 받는 설치 슬롯 |
| ApprovedDirections | 최초 기본값은 두 방향 모두. 어느 한쪽 주행이 미검증이면 그 에셋을 양방향 승인 목록에서 제외 |

지지대가 장식이면 배치 검사에서 제외할 수 있지만 실제 차량도 그 지지대에 막히지 않아야 한다. 실제 주행을 막는 기둥·지형·시설은 Solid 검사 대상이다. 눈에 보이는 건물이라고 전부 검사하거나, 모든 지지대를 무조건 제외하지 않는다.

차량 통행 공간은 겉모습이 아니라 실제 이동 충돌체를 수용해야 한다. 현재 ACharacter 기반에서는 수직 캡슐의 실제 크기와 경사에서의 공간을 검증하고 예산을 정한다. 임의의 차고 수치를 확정값으로 넣지 않는다.

## 4. 두 방향과 소켓 좌표계

기존 소켓 규약을 살릴 수 있게 A→B를 제작 기준으로 한다. 기존 Snap_In을 A, Snap_Out을 B에 매핑할 수 있으며 파일·소켓을 지금 바꾸지는 않는다.

- A/B 소켓의 로컬 +X: A→B 주행 방향.
- 소켓 +Z: 해당 연결부 도로의 위쪽.
- ReverseFrame(F): F의 로컬 +Z를 중심으로 180도 회전. +X/+Y를 반대로 하고 +Z를 유지한다. 월드 Z축 회전이 아니다.

| 선택 방향 | 입구 주행 프레임 | 출구 주행 프레임 |
|---|---|---|
| A→B | PortA | PortB |
| B→A | ReverseFrame(PortB) | ReverseFrame(PortA) |

기존 코스 끝의 프레임은 항상 다음으로 진행하는 주행 방향이다. 새 입구 프레임과 기존 끝 프레임을 일치시킨다.

열벡터 변환행렬 표기:

```text
PieceWorld = TailWorld × inverse(EntryLocalForDirection)
NextTailWorld = PieceWorld × ExitLocalForDirection
```

이 식은 개념 표기다. UE FTransform의 합성 순서를 그대로 복사하는 코드가 아니며 실제 구현에서 엔진 규약과 대조한다.

같은 조각이라도 B→A에서는 중심선 순서를 뒤집고 진행 접선도 반대로 한다. 총길이가 L이면 기준 A→B 거리 s는 역방향에서 L-s다. 표면 Up은 뒤집지 않는다. 체크포인트 통과 방향과 안전 복귀 방향도 선택 방향을 따른다.

방향별 안전 복귀 위치가 같다고 가정하지 않는다. 위험 슬롯의 위치는 메시와 함께 변환하되, 방향을 가진 패드 등은 의도에 따라 방향별 데이터나 지원 규칙을 둔다.

## 5. 배치 후보 계산과 판정

후보 계산과 검사는 월드를 변경하지 않는 조회 함수로 둔다. 서버와 클라이언트가 동일한 데이터·기하 규칙을 사용한다. 단, 클라이언트의 월드 준비 상태가 부족하면 유효한 것처럼 표시하지 않고 확인 중으로 둔다.

```text
EvaluatePlacement(CourseSnapshot, PieceDefinition, Direction, PlacementRules)
  1. 조각·방향·데이터 준비 확인
  2. 현재 Tail로 정확한 후보 Transform 계산
  3. 연결 규격·Transform·지원 주행 자세 검사
  4. 도로의 고도·월드 경계 검사
  5. 기존 코스·보호 공간과 간섭 검사
  6. 후보 출구의 자동 도착 구간을 계산하고 동일 안전 검사
  7. CandidateTransform, NextTail, FinishReservation, Issues 반환
```

요청 권한·Epoch·Revision 검사는 서버 요청 계층이 먼저 수행한다. 공간 검사를 통과해도 요청 권한이 생기지는 않는다.

### 연결 검사

- 포트 존재, 유한 좌표, 유효 스케일, 폭·연결 프로파일 호환을 검사한다.
- 자동 정렬 후 입구 위치·전방·Up이 기준에 맞는지 검사한다. 실패하면 데이터 또는 계산 오류다.
- 도로의 경사·뱅킹은 차량에서 검증한 지원 범위를 넘지 않아야 한다. 숫자는 주행 시험 후 결정한다.
- 전역 진행 방향, 코스의 총 회전각, 종점이 시작점과 가깝다는 조건은 검사하지 않는다.

### 고도와 월드 경계

- 경계는 월드의 일관된 기준으로 정의한다. 카메라 위치·화면 위아래를 기준으로 삼지 않는다.
- 고도는 도로 영역의 월드 최소·최대 높이로 검사한다. 장식 지지대 길이가 고도 제한을 바꾸지 않는다.
- 입출구만 검사하지 않는다. 곡선·경사의 중간 최고점도 포함한다.
- 차량 통행 공간의 유효성은 별도 Clearance 검사이며 도로 고도와 다른 거절 사유로 표시한다.
- 직사각형 Bounds를 최종 높이 근거로 사용할 때 실제 도로를 과도하게 감싸지 않게 제작한다. 필요하면 더 작은 구간으로 분해한다.

### 간섭 검사

처음에는 기존 조각 목록을 순회한다. 전체 AABB로 후보를 추린 뒤 작은 OBB들의 분리축 검사 등으로 실제 겹침을 판정한다. 필요 시 엔진의 검증된 형상 쿼리로 대체할 수 있으나 결과 계약은 동일하다. 대규모 공간 인덱스는 측정된 필요가 있을 때 추가한다.

| 비교 대상 | 기본 판정 |
|---|---|
| 후보 Solid ↔ 기존 Solid | 실질 관통이면 거절 |
| 후보 Solid ↔ 기존 DriveClearance | 기존 길을 막으므로 거절 |
| 후보 DriveClearance ↔ 기존 Solid | 새 길을 달릴 공간이 부족하므로 거절 |
| 후보 DriveClearance ↔ 기존 DriveClearance | 겹친다는 이유만으로 거절하지 않음 |
| 후보 Solid ↔ 기존 체크포인트/복귀 보호 공간 | 보호 공간 침범이면 거절 |
| 후보의 체크포인트/복귀 보호 공간 ↔ 기존 Solid | 새 보호 공간을 확보하지 못하므로 거절 |

도로 위를 다른 도로가 지나가도 실제 도로·차량 공간이 침범하지 않으면 허용한다. 평면 중심선 교차만으로 거절하지 않는다. 운전 중 움직이는 장애물의 전체 이동 범위는 그 장애물 설치 계약에서 확보하며 장식 효과와 혼동하지 않는다.

후보 하나를 N개 기존 조각과 비교하고 조각당 검사 Shape 수가 K 수준이면 최악 비용은 대략 O(NK²)다. 두 방향이므로 후보 비용은 상수배다. 실제 비용은 에셋 Shape 수와 월드 수량으로 측정한다.

### 접합부 예외

직전 조각 전체를 Ignore하지 않는다. 예외는 실제로 맞붙는 두 포트의 작은 JoinCollar에만 적용한다.

- 본체와 JoinCollar의 검사 Shape를 명확하게 구분한다.
- 연결된 Collar 쌍에서 합의한 작은 접촉·수치 오차만 허용한다.
- 본체↔본체와 본체↔상대 Collar는 계속 검사한다.
- 해당 Collar Shape가 지정된 짧은 영역을 벗어나면 에셋 정적 검사에서 실패시킨다.
- 겹침 허용 오차를 전 트랙에 큰 여유값으로 적용하지 않는다.

이를 통해 정상 접합은 허용하면서 새 U자 조각이 직전 조각 몸통으로 돌아와 관통하는 배치는 거절한다.

## 6. 자동 도착 구간의 예약과 수명

도착 시스템은 다음 두 부분으로 나눈다.

1. 통과 도로 구간: 입구·출구·결승/체크포인트 기준면을 갖는다. 다음 라운드에도 유지한다.
2. 마감 시설: 끝막음·종료용 연출 등 확장 때 제거할 임시 부분이다.

새 후보를 평가할 때마다 후보 출구에 이 두 부분을 가상 배치하고 공간을 검사한다. 아직 액터로 생성하지 않으며 데이터로 예약한다. 각 조각이 확정될 때 예약도 같은 Revision으로 교체한다. 이전 Tail의 예약은 새 후보 검사에서 대체 대상으로 처리하며, 실제 확정 도로를 Ignore하는 것으로 확대하지 않는다.

항상 다음 불변조건을 유지한다.

```text
확정된 현재 Tail에는 안전한 도착 구간 예약이 존재한다.
```

이 예약은 그 순간의 종료 가능성만 보장한다. 다음 조각을 추가할 공간이나 남은 모든 플레이어 조각의 배치 가능성은 보장하지 않는다.

건설 마지막 조각에서는 조각과 도착 구간을 모두 준비한 뒤 함께 확정한다. 생성·로드·등록 중 하나라도 실패하면 해당 요청에서 만든 준비 객체를 정리하고, 이전 코스·이전 예약·Revision을 보존한다. 완료 표시를 먼저 갱신하지 않는다.

다음 라운드 확장 시에는 이전 결승의 통과 도로를 유지하고 기존 체크포인트를 보존한다. 마감 시설만 제거하며 그 통과 도로의 출구를 새 Tail로 쓴다. 건설이 막혀도 이전 구간을 복구하거나 명시적으로 종료할 수 있도록 이전 상태를 보존한다.

초기 시작 도로도 플레이를 열기 전에 도착 가능한 기본 상태인지 검사한다. 다음 라운드에서는 이전 마감 시설을 제거한 확장용 상태를 먼저 가상으로 평가하고, 첫 새 조각이 확정될 때 실제 마감 시설을 대체한다. 그 전까지 이전의 종료 가능한 코스를 보존한다. 이미 도착 도로가 생성된 상태의 종료 가능성은 그 도로와 마감 시설로 증명하며, 그 출구에 도착 도로를 하나 더 붙이는 검사를 재귀적으로 반복하지 않는다.

점수는 물리 Actor 수와 구분한다. 자동 도로는 플레이어당 조각 수 N에 포함하지 않고 추가 점수도 자동 부여하지 않는다. 기존 조각별 체크포인트 정책을 유지한다면 마지막 조각의 논리적 CheckpointId가 도착 도로 기준면을 사용하게 하여 결승·체크포인트 중복 지급을 막는다. 이전 라운드 결승의 ID와 기준면은 확장 뒤에도 유지한다.

자동 도착 구간 자체의 경사·복귀 위치·장애물 공간 역시 사전 검증한 데이터여야 한다. 공간 검사 성공을 모든 차량의 완주 가능성 증명으로 취급하지 않는다.

## 7. 전체 경로와 진행 방향

기존 경로는 순서가 있는 목록으로 관리한다. 새 조각을 Tail에 정확히 붙이면 기존 연결성을 다시 탐색할 필요는 없다. 새 조각의 공간은 모든 관련 기존 조각과 비교한다.

각 목록 항목에 PieceId, Direction, Transform, Sequence와 길이를 둔다. 시스템 도착 도로도 실제 주행거리에는 포함하되 점수 대상 ID와 구분한다.

코스 진행거리를 사용할 경우:

```text
진행거리 = 해당 구간 전까지의 누적길이 + 해당 방향 기준 구간 내 거리
```

차량 위치를 전체 중심선 중 단순 최단거리 지점으로만 투영하지 않는다. 직전 구간·허용 인접 구간·체크포인트 순서를 함께 사용해 입체 교차에서 다른 도로로 진행도가 튀지 않게 한다. 실제 거리 차 탈락 지표 채택은 기존 경기 규칙의 미정 계약으로 남겨 둔다.

P0에는 전체 미래 경로 탐색, 무한 조각 조합 탐색, 총 회전각 제한을 추가하지 않는다. 필요하면 별도 기능으로 검토한다.

## 8. 실패 원인과 미리보기

판정은 bool 대신 Issues[]를 반환한다. 각 이슈에는 코드, 문제 Shape/구간, 충돌 상대 ID, 문제 위치·범위, 현재 값·허용값, 관련 코스 Revision을 포함한다. 내부 ID를 그대로 게임 UI에 출력하지 않는다.

| 이슈 | 사용자 표시 예시 | 시각 표시 |
|---|---|---|
| DataNotReady | 트랙 정보를 준비 중입니다 | 회색 Ghost·로딩 |
| ConnectorMismatch | 연결 규격이 맞지 않습니다 | 접합부 강조 |
| UnsupportedPose | 이 기울기는 지원하지 않습니다 | 문제 구간의 기울기 표시 |
| AboveHeightLimit | 트랙이 높이 상한을 넘습니다 | 초과 구간·상한면 |
| BelowHeightLimit | 트랙이 높이 하한을 넘습니다 | 초과 구간·하한면 |
| OutsideBuildBounds | 건설 가능 범위를 벗어납니다 | 경계·초과 부분 |
| TrackOverlap | 기존 트랙과 겹칩니다 | 양쪽 충돌 구간 |
| InsufficientClearance | 차량이 통과할 공간이 부족합니다 | 부족한 통행 공간 |
| ProtectedAreaBlocked | 체크포인트·복귀 공간을 침범합니다 | 보호 영역 |
| FinishAreaBlocked | 도착 구간을 만들 공간이 부족합니다 | 자동 도착 Ghost |
| StaleRevision | 코스가 변경되었습니다. 다시 확인해 주세요 | 최신 Tail로 Ghost 갱신 |

대표 원인은 고정된 우선순위로 선택하고 다른 이슈 수를 함께 알린다. 후보 계산을 막는 데이터 오류를 우선하고, 기하 판정에서는 연결/지원 자세→높이/경계→실제 도로 관통→통행 공간→보호 공간→도착 구간 순으로 한다. 같은 종류 여러 충돌 중에는 안정 ID/Shape 순서를 사용해 메시지가 매 프레임 바뀌지 않게 한다.

실제 도착 후보에서 발생한 높이·간섭 오류는 FinishAreaBlocked의 상세 원인으로 포함한다. 사용자는 현재 조각과 자동 도착 부분 중 어디가 문제인지 알 수 있어야 한다.

로컬 입력 흐름:

- 선택 모드에서 후보를 고른다.
- 배치 모드에서 현재 Tail에 스냅될 결과를 보여준다. 마우스 위치는 스냅 의도/카메라 조작에 쓰며 최종 월드 Transform을 임의로 바꾸지 않는다.
- 기존 휠 회전 입력의 한 단계는 두 방향을 토글한다. 부호가 달라도 두 상태에서는 다음 결과가 같다. 입력 이벤트를 한 단계당 한 번 소비한다.
- 현재 방향과 반대 방향을 모두 평가해 반대 방향이 유효한지 표시한다. 유효 방향으로 자동 전환하거나 자동 설치하지 않는다.
- 설치 대기 동안 중복 요청을 막는다. 서버 거절은 실제 반환 사유를 표시한다.
- 기존 취소 액션 제외·줌 후속 정책을 유지한다. 새로운 조작을 필수로 늘리지 않는다.

Ghost·이유·도착 예약은 같은 후보 평가 결과를 소비한다. 별도 시각 전용 계산기로 다른 위치를 보여주지 않는다. 캐시 키는 Piece/DefinitionVersion/Direction/CourseRevision/RulesVersion/관련 공간 상태로 잡고 변화 시 재평가한다. 무관한 UI 변경 때문에 매 Tick 전체 코스를 다시 검사하지 않는다.

## 9. 서버 요청과 한 번의 확정

요청은 소유 PlayerController 경로로 다음 값만 보낸다.

```text
OfferedPieceId, Direction(AtoB/BtoA), RoundEpoch, SeenCourseRevision, ClientRequestId
```

서버는 임의 월드 Transform, 클래스 경로, 클라이언트의 유효 판정을 수용하지 않는다.

```text
소유 참가자·Phase·기한·Epoch·후보·방향·배치 잔여권한 확인
→ 요청 ID 중복 확인
→ 최신 Revision 확인
→ 서버 월드로 EvaluatePlacement
→ 조각 및 필요한 도착 객체 준비
→ 준비 성공과 최신 조건 재확인
→ 목록·Tail·예약·플레이어 완료·Revision을 한 번에 확정
→ 상태 복제 및 요청 결과 전달
```

게임 스레드에서 동기 처리하는 최소 구현을 우선한다. 비동기 로드가 필요하면 승인 카탈로그를 건설 진입 전에 준비하고, 늦은 완료가 이전 Epoch/Revision에 반영되지 않게 한다.

동일한 플레이어+Epoch+RequestId의 재수신에는 기존 결과를 돌려주고 재생성하지 않는다. 오래된 Revision은 선택을 보존한 채 명시 거절한다. 최신 Tail로 자동 재배치·자동 재요청하지 않는다.

동시 요청은 서버 처리 순서로 한 개씩 확정한다. 첫 요청의 성공 뒤 이전 Revision으로 온 다른 요청은 재확인이 필요하다. 서버 결과를 먼저 본 호스트와 원격 수신 클라이언트 모두 동일한 표시 갱신 경로를 사용한다.

복제는 확정 PieceId/Direction/Transform/Sequence, 코스 Revision/Count/Tail, 도착 상태를 전달한다. 다른 Actor의 도착 순서는 가정하지 않는다. 최신 Revision의 실제 트랙·도착 도로·충돌이 준비된 뒤 준비 응답을 보내고 서버가 Countdown을 시작한다.

## 10. 시간초과와 막힌 코스

제한시간이 끝나면 서버의 작은 승인 대체 목록을 정해진 순서로 평가한다. 각 후보의 두 방향에 동일한 높이·간섭·도착 예약 검사를 적용한다.

- 기본 직선도 예외로 강제 설치하지 않는다.
- 유효한 대체가 있으면 정상 요청과 같은 생성·확정 경로를 사용한다.
- 남은 참가자에 필요한 대체가 모두 실패하면 ConstructionBlocked로 예외 종료한다.
- 정상 N개 추가 완료로 기록하지 않는다. 이전 확정 코스와 종료 가능한 도착 예약을 보존한다.
- 예외 결과 뒤 기존 코스로 계속 경주하는 정책을 묵시적으로 추가하지 않는다. 우선 기존 문서의 명시 예외 종료를 따른다.

도착 예약이 있기 때문에 현재 코스를 마감할 공간은 확보되지만, 남은 모든 조각을 배치할 수 있다는 뜻은 아니다.

## 11. 첫 구현의 순서

1. 직선·비대칭 커브·완만한 경사로 A/B 연결 프레임과 역방향 데이터 확인.
2. 두 방향 Transform·고도·경계 검사와 문제 위치 시각화.
3. 작은 OBB 기반 Solid/DriveClearance 검사 및 국소 접합 예외.
4. 매 배치의 도착 구간 예약과 마지막 설치의 일괄 확정.
5. Ghost·대표 원인·반대 방향 가능 표시를 같은 판정 결과에 연결.
6. 서버 요청·stale·중복·생성 실패·동시 처리·복제 준비 확인.
7. 제한된 타임아웃 대체와 ConstructionBlocked 경로.

에셋 Validator는 포트·프레임·양방향 경로·Footprint·Collar·방향별 복귀 데이터 누락을 먼저 검사한다. 실제 월드 간섭과 주행 성공은 런타임 통합에서 별도로 확인한다. Centerline과 양방향 메타데이터를 실제 소비하므로 기존 문서의 선택 필드를 필수로 바꿀 범위는 구현 작업에서 생산자·소비자와 함께 갱신한다.

## 13. 실측으로 정할 값

아래 값은 중앙 PlacementRules와 제작 규격에서 관리하고 아직 고정 수치를 넣지 않는다.

- 월드 높이 상한·하한과 수평 건설 범위.
- 연결 폭·Transform 오차, 접합부 허용 오차와 Collar 길이.
- 실제 차량 충돌체를 수용하는 폭·머리 공간·여유값.
- 지원 경사·뱅킹과 자동 도착 도로 규격.
- 곡선의 검사 Shape·경로 샘플 간격, 보수적 형상의 허용 오차.
- 체크포인트 기준면·방향별 안전 복귀 위치와 보호 공간.

구현 착수 전 필요한 최소 산출물은 검증된 직선·비대칭 커브·경사 각 1개, 양방향 데이터, 도착 모듈 1개, PlacementRules 초안이다. 원작의 미공개 수치를 추측해서 호환성 기준으로 삼지 않는다.
