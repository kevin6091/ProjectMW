# 결과판과 시상 이름판 글자 여백 검증

`feature/match-results-tally@ddc272f` 이후 Client UI 작업이다. Switch 영상의 체크포인트 `F33829`, 복귀 `F8274`, 집계 `F29176`, 누적 순위 `F30020`, 시상 `F30352`를 기준으로 화면 역할과 글자 배치를 대조했다. 같은 내용의 전후 픽셀 실측은 4인 표시 전용 데이터와 동일한 뷰포트를 사용했다.

## 편집 위치

| WBP | 편집 지점 | 변경 |
| --- | --- | --- |
| `WBP_MatchResults` | `TallyHeading`, `TallySignFace`, `TallySignLogo` | 제목 위치를 디자인 Y 기준 −31에서 −29로 옮기고, 판과 로고 상단을 17 디자인 단위 올렸다. 제목 획 높이와 판 바닥·막대의 세로 영역을 유지하면서 제목 위 여백을 확보했다. 가운데 만점 열의 등수와 제목이 동시에 보이도록 배치를 확인했다. |
| 같은 WBP | `TallyWidthByPlayerCount` | 3인 940→976, 4인 1252→1300으로 열 영역을 넓혔다. |
| `WBP_MatchScoreColumn` | `TallyScoreMarker`, `TallyScoreLine`, `TallyScoreFit` | 좌우 안쪽 여백 13→15, 위 여백 9→13, 배지 뒤 간격 10→7. 배지는 기존 크기로 표시한다. 나머지 폭을 숫자에 배정해 긴 숫자만 필요한 만큼 맞춘다. |
| 같은 WBP | `RankSuffix` | Noto Sans KR Bold의 글꼴 크기를 24.75→32pt로 높이고 하단 패딩을 32→30으로 조정했다. 접미사가 작고 옆에 붙는 서수 관계와 아래 획의 기준선을 확인했다. |
| `WBP_MatchPodiumCard` | `PodiumNameFit` | 카드의 로컬 좌표에서 이름 왼쪽에 10, 오른쪽에 8 디자인 단위 여백을 추가했다. 기존 왼쪽 기준 확대 피벗과 사용 가능한 폭에 맞추는 규칙을 재사용했다. 별도 잘림 설정 대신 슬롯 자체에서 공간을 확보했다. |

제목·숫자·이름의 편집값은 WBP에 있다. 가산, 입력, 카메라, 경기 전환의 런타임 코드는 그대로 사용했다.

## 실제 글자 단면

Switch 원본 `F30020`의 1920×1080 누적 순위 제목은 판 윗변과 약 34px 간격이고 실제 밝은 획 높이는 78px다. 1위 숫자 높이는 약 101px, 영문 접미사는 약 50px였다. 접미사는 숫자보다 아래에서 시작하며 두 요소의 아래 획은 같은 높이에 놓인다. 프로젝트의 한글 `위`는 별도 글리프이므로 간격과 기준선 위주로 비교했다.

| 계측 항목 | 수정 전 | 수정 후 |
| --- | ---: | ---: |
| 제목 위 여백, 1920×1062 | 10.6px | 29.3px |
| 제목 위 여백, 1280×720 | 6.6px | 20.0px |
| 제목 위 여백, 800×482 | 4.1px | 12.7px |
| 1280×720의 1위 접미사 획 높이 | 21px | 26px |
| 1280×720의 1위 숫자와 접미사 아래 획 차이 | 2px | 0px |
| 같은 창에서 첫 열 다섯 자리 획 너비 | 103px | 103px |
| 같은 창에서 첫 열 `999999` 획의 막대 오른쪽 여백 | −9.8px | 10.2px |
| 같은 창에서 1위 카드 이름 슬롯 왼쪽과 메달 오른쪽 간격 | −1.4px | 9.8px |

여백이 음수인 셀은 겹침 또는 넘침이다. `999999`는 PIE 표시 위젯에만 넣은 여섯 자리 시험값이다. 이 조건에서 호스트의 오른쪽 여백은 −21.5→19.7px, 작은 창은 −7.8→4.9px였다. 밝은 글자 마스크는 표시된 픽셀에서 구했고 수치에 적은 슬롯 경계는 Unreal 위젯 기하로 읽었다. 점수의 밝은 외곽선은 마스크에 포함된다. 메달 숫자의 어두운 외곽선은 캡처로 확인했다.

## Cua Driver 실행 조건

| 장면 | 확인 결과 |
| --- | --- |
| 체크포인트, 복귀, 재출발 | 실제 3인 Listen Server PIE에서 2라운드 체크포인트와 결승 트리거를 확인했다. 시험에서 차량 위치를 지정했다. 낙하 뒤 호스트 복귀 대기 0.8초와 입력 가능 상태 복구를 서버 로그에서 읽었다. 호스트 화면에서 선수명, 계기판과 원형 복귀 표식을 확인했다. 긴 시험 이름은 출발 대기에서 차량이 밀집하면 겹칠 수 있다. 일반 주행으로 접근하는 동안의 모든 이름 배치는 미검증이다. |
| 라운드 집계 | 세 창에서 라운드 소개, 체크포인트 점수, 완주 점수, 선착 보너스, 누적 순위를 관찰했다. 체크포인트 가산과 누적 순위 사이의 제목·배지·점수는 호스트 연속 캡처에 있다. |
| 저점수·만점 동점·DPI | 1920×1062 / 1280×720 / 800×482에서 긴 한글·영문 이름, 0/50/120/500점, 네 열과 만점 동점을 검증했다. PIE의 UE UI `ApplicationScale`을 100→125%로 바꿔 세 창의 만점 화면을 다시 캡처했고 100%로 복구했다. OS의 모니터별 배율 전환은 별도 검증이 필요하다. 표시 전용 테스트에서는 배경에 주행 HUD가 남아 있을 수 있다. |
| 최종 순위표·시상 | 세 창에 동일한 긴 한글·영문 이름과 1~3위 데이터를 넣고 정착 화면을 확인했다. 원본 시상의 카드 상하 여백과 메달·이름·차량 배치를 참고해 이름의 가용 폭을 조정했다. 결승 카메라와 1위 차량 컷신이 이어지는 실제 매치 종료, 확대가 시작되는 단일 프레임은 이번 실행에서 확인하지 못했다. |

[실제 경기와 시상 표본](Evidence/ResultsTypography/race-text-samples.jpg) · [라운드·복귀·DPI 로그](Evidence/ResultsTypography/race-events.jsonl) · [세 창 단계 로그](Evidence/ResultsTypography/pie-stages.txt)

호스트의 세 구간을 77/46/83장, 약 13.0/8.0/13.3초로 표본 채집했다. 이 자료의 간격보다 짧은 한 프레임 넘침은 판정할 수 없다. 최종 경기 진입을 앞당기기 위해 테스트 Editor 메모리에 넣은 목표 점수 변경 상태에서 자동 승인 검토가 PIE 실행을 막았다. 목표를 4,000으로 복구한 후 원본 GameMode 패키지를 디스크에서 다시 읽었다. GameMode SHA-256 `DC4C06640563F99B7EC4D36C3B21B8E8589CCCFCCAEF93A2A0B5D5249A4888EC`가 작업 전후에 일치한다.
